# UI 设计规范

[English](ui-design.md)

这是 Web、桌面和原生 App 的共同设计规范，适用于所有新增、修改的界面及设计审查。平台指引规定组件选择，[UI 文案规范](ui-copy.md)规定措辞。既有页面在修改时遵循本规范；本文不代表已完成全产品改造。

**用布局、图标和交互表达，让界面本身告诉用户怎么用。Keep it simple。** 用户应能从结构和控件看出当前对象、状态和下一步。标签说明名称与动作，描述文字只补充界面无法清晰、安全表达的必要信息。

## 产品原则

适用于所有实现，不限于某个功能。

1. **常用功能放在顺手的位置。** 从用户使用视角设计，最常用的操作最显眼。按钮、卡片、列表清晰可见；用底色和间距区分区域，尽量不用边框。
2. **用排版讲述功能。** 用布局和图标表达功能，不放长段说明。确实需要解释时，放在 info 图标按钮里，悬停或点击后以 tooltip 或弹出层显示。
3. **动线自然、步骤最少。** 流程贴合用户想做的事，让 80% 的常见任务用最少的步骤完成。
4. **不让用户迷惑。** 每个空状态都引导到下一个有用的操作；有先后顺序的困难配置拆成 stepper；彼此相关的决定放在同一步。
5. **帮助触手可及。** 提供相关文档的跳转链接，或一键复制、可直接拿去问 Bot 的 prompt。

## 设计规则

1. **先设计结构，再补充说明。** 用层级、距离、留白和分组表达关系与重点。如果需要一段话解释该看哪里、该用哪个控件，先调整布局或控件。辅助描述按需出现，每行不必固定配一句说明。
2. **使用熟悉的组件和图标。** 遵循所在平台或应用外壳的组件规范。手机遵循[移动端设计](../../apps/mobile/DESIGN.md)的原生组件规则；底部 sheet 和选择器遵循[原生 sheet 标准](../../apps/mobile/DESIGN.md#bottom-sheets)（以 Composer 的模型选择（Model Choice）选择器为准：系统 sheet 背景、原生列表与语义色、原生关闭按钮），`pnpm lint` 无基线强制执行；Web 和桌面遵循 [DSH UI](../../.agents/skills/dsh-ui/SKILL.md)。图标帮助识别对象、动作和状态。不熟悉或影响重要的操作保留简短可见标签；纯图标操作必须有无障碍名称。含义不能仅靠颜色表达。
3. **让流程解释任务。** 将当前需要决定的事及相关信息放在一起，突出主要操作，立即回应输入，并就地显示进度、成功或可恢复的失败。确实需要先后决策时才分步，简单任务在同一处完成。
4. **按需展示细节。** 次要说明、背景和诊断信息放在名称明确的展开项或帮助入口中。当前决策需要的信息直接放在操作旁边。不能为了简洁而把必要指引或后果藏起来。
5. **保留必要文字与事实。** 简短标签、单位、当前值、权限范围、隐私边界、不可逆后果和可操作的错误信息仍需明确。安全核对必须在确认前展示完整必要值。简洁不意味着截断指纹、替用户决定或削弱知情同意。
6. **不同使用方式下都可操作。** 保留清晰阅读顺序、键盘与焦点操作、屏幕阅读器名称和可达按钮。大字号允许换行与滚动。明暗主题及维护的语言遵循同一信息层级，各平台使用自己的组件和外观。
7. **所有面板一套设计语言。** [桌面与 Web 界面决策](../decisions/desktop-ui.md#adr-0028) 汇总当前设计系统约定。Web 和桌面的面板都用 `ds/` 里的共享组件（`NavItem`、`SettingsSection`、`SettingsRow`、控件、对话框）拼装，组件只读 `ds/tobs.stylex.ts` 里的风格令牌（`style.*`，[ADR-0351](../decisions/desktop-ui.md#adr-0351)）。选中只改变颜色和文字字重，不改边框或尺寸。面板之间用露出底色的间隔分开，不用线；边框只留给输入框和焦点环。`scripts/check-design-tokens.mjs` 会拦下 `ds/` 以外新增的 `bh-` CSS 规则、`stylex.create` 里的颜色字面量、内联样式字面量和新增的分隔线边框。
8. **内容在固定头部下自由滚动。** 松手后内容停在平台自身滚动惯性停下的位置，应用不额外吸附，与 iOS 和 Android 一致；只有 iOS 大标题或 Material 可折叠顶部应用栏才会吸附。程序触发的滚动（例如键盘弹出时的滚动）不能停在标题区块中间（[#5186](https://github.com/BotHarness/DeepSeekBot/issues/5186)）。

## 大字号

内容跟着系统字号一起放大；导航栏这类空间固定的地方保持原尺寸，另给用户看清的办法。每个控件属于下面三种之一：

| 位置                                   | 字号变大时                                                                                                                                                                                      |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 正文、列表行、表单                     | 全部放大。文字换行，不为省空间截断；辅助功能字号（AX1–AX5，`theme.largeText`）下并排的元素改为上下排。                                                                                          |
| 图标加文字的按钮和行                   | 保留图标，并和文字一起放大：尺寸取文字的字体角色乘以 `theme.fontScale`，SwiftUI 符号用带 `textStyle` 的字体。放不下时让文字换行或把控件竖排，不要隐藏图标。                                     |
| 导航栏、工具栏、sheet 顶部的纯图标按钮 | 不随字号放大。有原生栏按钮就用原生的，iOS 长按会弹出放大预览（Large Content Viewer）；自绘的统一用顶栏按钮的 `xxxLarge` 上限。每个都要有无障碍名称，可点区域至少 44pt（iOS）/ 48dp（Android）。 |

`node scripts/check-ui-rules.mjs`（在 `pnpm lint` 中）会拦下：文字旁边写死尺寸的图标（`unscaledLabelIcon`）、固定尺寸框里跟着放大的图标（`fixedIconScale`）、跟着字号放大的 Compose 图标按钮（`scaledActionBox`）。平台细节见[移动端代码规则 2](../../apps/mobile/DESIGN.md#code-rules) 和[大字号验收约定](../../apps/mobile/DESIGN.md#system-text-and-large-text-acceptance)。

## 示例

| 场景       | 由界面表达                                                   | 保留的文字                                                     |
| ---------- | ------------------------------------------------------------ | -------------------------------------------------------------- |
| 配对电脑   | 电脑身份、分组指纹卡片、聚焦的核对步骤，随后进入手机批准步骤 | 完整指纹、简短核对指引、明确的一致／取消操作；详细说明按需展开 |
| 选择设置   | 分组行、当前值及合适的开关、选择器或分段控件                 | 名称和值；只有控件无法表达的后果才加提示                       |
| 保存或重试 | 立即显示处理中，成功可见，失败在相关操作旁呈现               | 具体动作名称和简短恢复指引                                     |
| 授权或移除 | 确认位置展示对象与范围，主次操作明确                         | 权限范围、不可逆后果，以及含义明确的取消／确认标签             |

## 审查标准

每个改动流程都要检查：

- 不读大段说明，也能识别对象、当前状态与下一步。
- 每句描述都提供必要事实，交互本身由布局、控件和反馈表达。
- 次要细节可以按需查看，知情决策所需事实直接可见。
- 图标、标签与无障碍名称含义一致，信息不只依赖颜色。
- 在平台输入方式、大字号、明暗主题及维护的语言下可以完成任务。未验证的平台和无障碍模式单独记录。

按相应平台要求做运行验证，并提供 PR 证据。缩短一段说明或截一张漂亮图片，本身不能证明交互可用。

## 请求卡片

聊天、活动中心和桌面伙伴里的审批、提问、授权等请求卡片遵循同一条排版规则。

- **一个内容内边距。** 每一行从同一条左边线开始。桌面和 Web 端内边距是 `space.x4`（12px）：聊天里由消息气泡提供，其他位置由卡片的 `inset` 样式提供，二者不叠加。原生端卡片用 `space.x5`（16px）。
- **一个行间距。** 标题、主体、警告、说明和按钮组之间只用一个间距：桌面和 Web 端 `space.x3`（8px），原生端 `space.x4`（12px）。卡片内部的嵌套分组（例如说明句和它下面的命令）沿用同一个间距，不另用更紧的值。
- **嵌套块对齐。** 命令、差异、选项列表这类底色块保留自己的内边距，但外边缘落在内容内边距上。当作一行使用的基础组件（例如可点击的摘要 `Button`）用 `paddingBlock`/`paddingInline` 清除内边距：StyleX 按属性具体程度解析，`xstyle` 里的 `padding` 简写会输给组件自身的长写属性。
- **阅读顺序。** 先标题和状态，再主体（说明句和命令或文件），然后是选择前必须读到的不可撤销影响和风险，接着是结果，按钮放最后。可以按需查看的背景信息（规则范围、Host 访问、工作目录、来源）放进 ⓘ 或“详情”，不在卡片上另起一行小字。卡片上方不放任何内容。

[UI 规则 `xstyleShorthand`](../../scripts/check-ui-rules.mjs) 会拦下通过 `xstyle` 传入的样式里的 `padding` 或 `margin` 简写。其余部分要在渲染出的卡片上检查：量一下两种主题下各行左边线和间距是否一致。

## 消息操作与读取失败

卡片操作使用 Web 的 `ds/action-button` 或原生端的 `primitives/button`。调用处只提供语义图标、简短操作名、强调程度、忙碌状态与原有回调；共享实现负责底色、图标颜色、换行、禁用和无障碍状态。次要按钮的底色应与消息气泡或设置表面有区别。操作颜色直接从全局 DSH 主题计算，避免顶层设置弹窗依赖 Bot 区域的祖先变量，忙碌时保留操作名称。

独立的读取失败使用 `ds/read-failure` 或原生端 `primitives/read-failure`，摘要简短，原生端诊断详情可展开。允许重新读取，但不得重放审批、消息或其他写入。审批与提问卡片保留原有请求校验和键盘焦点行为。

Session 维护使用按 Host 客户端及 Bot 私聊隔离的共享控制器。错误卡片与用量面板观察同一操作的忙碌状态和结果。压缩与新建会话都不重发消息；群聊和 Assignment 错误不提供这些操作，忙碌及权限拒绝仍由 Host 判定。
