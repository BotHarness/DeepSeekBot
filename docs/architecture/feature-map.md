# Product feature map and H-2 split plan

The inventory is a snapshot of `origin/main` at [`c01e7a043d91`](https://github.com/BotHarness/DeepSeekBot/tree/c01e7a043d91d68783484a60cb53e3d835186c33). The parallel H-2 splits of `packages/core/src/messaging/*`, `packages/core/src/memory/accepted.ts`, `packages/core/src/voice/calls.ts`, and mobile UI are in flight at this baseline. Recheck their landed paths before taking a move below. [H-2 #4521](https://github.com/BotHarness/DeepSeekBot/issues/4521)

First-party features remain built into the Host and non-replaceable. The split gives them the same ownership shape that authors can use as a reference for a future Bot Feature. A Plugin is the DSH-native lifecycle and packaging unit. A Bot Feature and its `botFeatures` Service are BotHarness-defined contracts. S1 uses Todo to exercise that contract and S4 specifies how external Source Events enter the existing Bot Inbox. [Product glossary](../../GLOSSARY.md), [Plugin spec #4202](https://github.com/BotHarness/DeepSeekBot/issues/4202), [S0 ADR #4204](https://github.com/BotHarness/DeepSeekBot/issues/4204), [S1 Todo #4206](https://github.com/BotHarness/DeepSeekBot/issues/4206), [S4 ingress #4208](https://github.com/BotHarness/DeepSeekBot/issues/4208)

## Current inventory

“Both bridge files” refers to the Host implementation in `methods.ts` and the Typert adapter in `rpc.ts`. Registration names refer to `createCore` or `apply` in `plugin.ts` unless the row names a separate Plugin. Storage lists the primary table and migration owners. Cross-feature migrations also update shared Channel, Session or PersonaBot records. Panel and settings entries identify consumers of the Host's data. ## Target layout

Use one composition entry per feature. A feature includes the files it needs. Todo, Browser, Computer and VRM already have separate DSH Plugin packages, so their existing package boundaries remain intact. Steps in this plan move the built-in code and its adapters. The SDK migration of those Plugins follows its own slices in #4202.

```text
packages/core/src/features/<feature>/
  register.ts      # declarations and registrations for this feature
  tools.ts         # tool definitions, effects and direct invocation
  prompt.ts        # named prompt contributions
  events.ts        # ingress through the Source Event and Bot Inbox owners
  methods.ts       # Host command and query handlers
  rpc.ts           # feature-specific argument and result adapters, where needed
  store.ts         # data queries, writes and lifecycle hooks
  migrations.ts    # this feature's published migration definitions
  cli.ts           # existing direct and live command adapters
packages/client/src/client/features/<feature>/
  bridge.ts        # feature calls and presentation adapters
  locale.ts        # matching English and Chinese keys
  panel.tsx        # Panel when the feature has one
  settings.tsx     # settings when the feature has them
  styles.ts        # feature styling when needed
```

- **Composition.** `plugin.ts` keeps startup order, kernel construction, Fibers and cleanup. It calls a feature's `register(ctx)` once with named dependencies. For features with wiring in several phases, the registration supplies the phase callbacks and the root invokes them in the original order. The declaration groups identity, version, scope, settings, tools with effects, prompt sections with IDs and budgets, Panel bindings, Host methods, CLI, ingress where applicable, and data lifecycle. This is the shape of the proposed S1 `defineBotFeature` declaration. H-2 keeps the current setup, effects and registration mechanisms behind that shape. Feature enablement for Plugins, automatic CLI, prompt budgets, and public event ingress land with their respective SDK slices.
- **Host bridge.** Move handlers and feature-specific dependency types out of `methods.ts`. Keep `createBridgeMethods`, the aggregate `BridgeMethods` type and the trusted Human context in the shared adapter. Move feature-specific argument validation and result shaping out of `rpc.ts` where its Typert contract permits it. Assemble the feature adapter slices and their method lists at the shared `BotharnessBridgeService` boundary. Keep the exposed names, parameter and error layouts, descriptor order, stream lifetimes and access gates. Use the same invocation-time Human lookup before dispatch. The DSH API Gateway keeps ownership of `/api`. [Current transport conventions](../../docs/client-bridge.md)
- **Client bridge and copy.** Move calls and presentation adapters to the Client feature folders. Keep shared transport and compatible exports at `bridge.ts`. Use existing `packages/host-client` readers wherever two Clients consume the same shape. Keep `locale.ts` as the namespace and catalogue composition point. Compose feature dictionaries with the same keys and current typing and fallback behavior. Use the same approach for the native English and Chinese dictionaries, preserving live exports of `t` and `useStrings`.
- **Schema composition.** Move existing migration definitions and their private SQL helpers into the owning feature's `migrations.ts`. Keep cross-feature table rebuilds, shared Channel or Session migrations, and other shared migrations in Host-owned modules. Each owner exports ordered lists. At the composition root, concatenate **contiguous runs** from those lists in the precise order of `BOT_HARNESS_SCHEMA_PLAN`. An owner with interleaved generations contributes several runs. For example, the slots between `memory-accepted-commit` and `memory-branch-head` include Workspace Grants, tool approval rules and Assignment access. Preserve each ID, array position, generation, module, body, dependency and rebuild flag. `defineSchemaPlan` assigns generations from array positions. Extend the existing migration snapshot check to resolve moved definitions and the explicit runs, and require exact equality with the published ordered snapshot. [Schema engine](../../packages/core/src/database/schema.ts), [Migration snapshot check](../../scripts/check-schema-migrations.mjs), [Published migration snapshot](../../scripts/schema-migrations.json)
- **Import direction.** A feature can import kernel contracts. Kernel modules depend on narrow Service Definitions and receive Providers from composition. Features call other features only through named Services, such as Channel admission or Workspace Grant authorization, with Providers injected by the Host. They share neither internal stores nor sibling implementation modules. `plugin.ts` and the schema and bridge composition roots may import feature registrations or manifests. A future rule in `scripts/check-package-boundaries.mjs` can enforce this graph with explicit composition entry points and Service Definition paths. [Current boundary check](../../scripts/check-package-boundaries.mjs)

## Storage

The Host owns one operational SQLite database. Features and Plugins declare their own namespaced tables and migrations. The Host validates and runs migrations. The same Host lifecycle covers Profile backup and restore, PersonaBot Deletion and data purge. Plugin data shares that database. A Host-owned KV or document store may support small data sets. Existing Git-backed Memory Repositories, Profile files, attachment bytes and DSH Session Persistence keep their current owners during H-2. Moving migration definitions leaves current table names and stored data intact. [Operational Database owner](../../packages/core/src/database/owner.ts), [Profile portability](../../packages/core/src/portability/package.ts)

S0 tracks four open questions. [S0 #4204](https://github.com/BotHarness/DeepSeekBot/issues/4204)

- **Table names.** How does the Host map a feature ID to a safe, unique SQL prefix and reserve first-party and shared namespaces? Which rules apply to existing tables?
- **Migration ownership.** How does the Host register and order Plugin migrations, authorize writes within the namespace, and handle missing or disabled Plugins, version mismatch, and cross-feature dependencies?
- **Lifecycle enumeration.** Which declarations identify Profile-scoped data, Bot-scoped records, and owned files? How do backup, restore, deletion and purge enumerate data for uninstalled Plugins or incompatible versions? How do explicit Bot share/export opt-ins differ from Profile backup membership?
- **KV or documents.** What namespace, Profile/Bot key scope, size and count limits, transaction behavior, versioning and lifecycle rules should a small-data store expose?
