# Product feature map and H-2 split plan

The inventory is a snapshot of `origin/main` at [`c01e7a043d91`](https://github.com/BotHarness/DeepSeekBot/tree/c01e7a043d91d68783484a60cb53e3d835186c33). The parallel H-2 splits of `packages/core/src/messaging/*`, `packages/core/src/memory/accepted.ts`, `packages/core/src/voice/calls.ts`, and mobile UI are in flight at this baseline. Recheck their landed paths before taking a move below. [H-2 #4521](https://github.com/BotHarness/DeepSeekBot/issues/4521)

Each product feature is owned by a Cordis-native Plugin that injects application-defined Tobs Services. The DSH-native Bundle, Profile and Patch own deployment and composition. Additive UI Slots are open, and replacement starts with individually loadable first-party Panels. Messages, Channel list and Workspace Control Rail retain shell-owned fallbacks. This revises #4202 for Panels. Bot Feature and its `botFeatures` Service remain application-defined contracts for per-Bot enablement. S1 uses Todo to exercise that contract and S4 specifies how external Source Events enter the existing Bot Inbox. [Product glossary](../../GLOSSARY.md), [Plugin spec #4202](https://github.com/BotHarness/DeepSeekBot/issues/4202), [S0 ADR #4204](https://github.com/BotHarness/DeepSeekBot/issues/4204), [S1 Todo #4206](https://github.com/BotHarness/DeepSeekBot/issues/4206), [S4 ingress #4208](https://github.com/BotHarness/DeepSeekBot/issues/4208)

## DSH construct map

This is the target ownership map for the 35 features above. Folder slugs and Service names describe proposed boundaries. The inventory above records current registrations, method names and authorities. H-2 extracts to these boundaries in stages. [DSH/Cordis Context](../../.agents/skills/dsh-plugin-dev/references/context.md), [DSH-first composition, ADR-0015](../decisions/bots.md#adr-0015)

- **Cordis-native.** Plugin, Fiber, Service injection and provision, and Event dispatch. The Host and browser run separate Cordis applications. Startup, Registration and disposal belong to the Plugin Fiber.
- **DSH-native.** Bundle, Profile, Patch, Agent Scope, Tool and System Prompt Section Registries, Skill Registry, Storage Domain, Typert, API Gateway and Slot cardinalities. The **DSH-native** Event names below use **Cordis-native** dispatch. [Pinned Bundle and Profile docs](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/docs/user/develop/basic/publish.md), [Pinned Typert Service](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/typert/registry/src/service.ts)
- **Application-defined.** Feature IDs, Tobs Service Definitions, Bot Feature and its Registrations, Source Event and Bot Inbox admission, Operational Database and migration catalogue, remote method families, Dock Panel registry and Tobs Slot names. Source Event ingress is a contribution to the existing admission owner. PersonaBot, Human and Channel authority still apply after any contribution resolves. A product feature belongs to a Plugin. Per-Bot enablement applies to declared Bot Features, following #4202. [Glossary](../../GLOSSARY.md), [Host composition](../../packages/core/src/plugin.ts), [Bot Feature spec](https://github.com/BotHarness/DeepSeekBot/issues/4202)

Read the Host slug as `packages/core/src/features/<slug>/plugin.ts` and the Client slug as `packages/client/src/client/features/<slug>/plugin.ts`. A package path identifies an existing Plugin to retain. A Client contribution may be loaded under the shell until its extraction is complete. A Panel Plugin is separately loadable from its feature's Client folder. **Bridge** is the feature's method group on the existing application-defined `BotharnessBridgeService` Typert remote Service. **Fetch** and **device** identify existing transport paths. A dash records no seam required at this boundary. [Host RPC and registrations](../../packages/core/src/bridge/rpc.ts), [Client composition](../../packages/client/src/client/index.ts), [Device routes](../../packages/core/src/devices/mount.ts)

The kernel supplies the PersonaBot Registry identity primitive, Session Ownership, Channel authority and Source Event admission before feature activation. Feature Services expose operations over those primitives. This keeps the shared lifecycle dependencies acyclic. The Registries column names contributions. **Tools**, **Prompt**, **Skills** and **Domain** are DSH-native. **Ingress** and **Migrations** are application-defined. Domain is the current Todo seam. Its migration into the Host catalogue is S0/S1 work. The Events column names the Cordis listeners or emitters a Plugin owns or shares with the kernel. A callback, SSE update or durable Source Event needs no extra Cordis Event by default. The Slot column uses the application-defined names from [UI seams](#ui-seams). Dock Panel registrations are logically keyed by definition ID.

## UI seams

Panels are the first replaceable UI unit. Each first-party content Panel below has a separately loadable Client Plugin. A DSH Profile or Patch disables the built-in Loader row and enables a replacement. Both Plugins use the same public Tobs `dockPanels.register` contract and the same stable definition ID when replacing the same role. The registry already rejects duplicate active IDs. Registration disposal removes the live implementation, while the workspace retains compatible saved placement and instance metadata. Preserve the definition ID, scope, applicability, accessible actions and binding contract. A replacement inherits no authorization from its ID, saved position or instance binding. This changes the Panel portion of #4202 and carries forward ADR-0203's public registry and ADR-0234's separation of implementation, instance, binding and position. S0 records the revised contract. [ADR-0203](../decisions/desktop-ui.md#adr-0203), [ADR-0221](../decisions/desktop-ui.md#adr-0221), [ADR-0234](../decisions/desktop-ui.md#adr-0234), [Spec #4202](https://github.com/BotHarness/DeepSeekBot/issues/4202), [S0 #4204](https://github.com/BotHarness/DeepSeekBot/issues/4204)

The cardinality is the target for each Tobs seam. The current implementation may use a native Slot, a Tobs Registry or inline composition. Additive Slots are open to first- and third-party Plugins. Use unique contribution IDs in a list and distinct namespaced keys in a keyed Slot. Tobs-owned keys stay reserved for the corresponding first-party contribution, except for the explicit Panel replacement contract. The pinned DSH Slot store provides resolution and priority, so the owner must enforce any key policy it promises. This is composition of trusted Client code. DSH Dockkit provides layout adapters, controller and geometry. Tobs' public Dock Panel registry is application-defined and uses Dockview in the current workspace. ### Required shell fallbacks

Declare one application-defined DSH `chain` Slot for each of Messages, Channel list and Workspace Control Rail. The owner mounts the first-party renderer as the native chain's fallback, giving it the lowest precedence. In the pinned API, selectors run in ascending numeric priority and return `null` to decline. The first match supplies the body. Fiber disposal removes its entry from the chain. DSH renders the owner fallback whenever no remaining selector matches. The pinned chain can retain the fallback mount where draft or DOM state requires it. [Pinned chain contract](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/client/ui-slots/src/index.ts), [Pinned chain renderer](https://github.com/deepseek-ai/deepseek-harness/blob/66491b05e3f05ad35bcdd4f6cd7ed26041d9e3db/packages/client/ui-slots/src/renderer.ts)

The shell keeps the role IDs, placement and navigation. Messages keeps Channel selection, windowing, retained composer state and its child workspace. Channel list keeps Roster selection, sorting and access. The Workspace Control Rail keeps Settings, required navigation and Dock state. The first release opens the additive points above. Any chain renderer use is scoped to an owner-approved presentation case. Disabling a required role or giving an external Plugin its entire surface is deferred. Verify the all-decline case, contribution disposal, Simple and Advanced layouts, narrow fallback and draft/selection continuity before opening a chain case. [Channel workspace ownership, ADR-0221](../decisions/desktop-ui.md#adr-0221), [Dock and shell integration](../../packages/client/src/client/workspace.tsx)

## Target layout

Use one Cordis Plugin entry per feature side. Todo, Browser, Computer and VRM already have separate DSH Plugin packages, so their package boundaries stay intact. Built-in features extract into feature folders and adopt the Plugin shape below. SDK activation, the Todo tracer and external ingress follow the #4202 slices.

```text
packages/core/src/features/<feature>/
  plugin.ts        # Cordis Plugin entry with named Service injection
  service.ts       # Service Definitions and Providers owned by this feature
  tools.ts         # tool definitions, effects and direct invocation
  prompt.ts        # named prompt contributions
  events.ts        # ingress through the Source Event and Bot Inbox owners
  methods.ts       # Host command and query handlers
  rpc.ts           # feature-specific argument and result adapters, where needed
  store.ts         # data queries, writes and lifecycle hooks
  migrations.ts    # this feature's published migration definitions
  cli.ts           # existing direct and live command adapters
packages/client/src/client/features/<feature>/
  plugin.ts        # Client Cordis Plugin for Slot contributions
  bridge.ts        # feature calls and presentation adapters
  locale.ts        # matching English and Chinese keys
  panels/<id>/plugin.ts  # separately loadable public Dock registration
  settings.tsx     # settings when the feature has them
  styles.ts        # feature styling when needed
apps/mobile/src/features/<feature>/
  strings.ts       # native feature copy, assembled by the mobile catalogue
```

- **Composition.** The root `plugin.ts` keeps kernel construction and startup order. Extract the feature wiring as an `apply(ctx)` entry with named Service injection, then mount it through native Cordis composition with effects owned by its Fiber. During a pure move, keep in-place calls or phase callbacks when a new Fiber would change event ordering, injection or cleanup. Review the later activation against the original phase order. Features that need per-Bot enablement use the application-defined Bot Feature contract. Tools, prompt sections, ingress, migrations and CLI adapters remain with their feature and use the existing registrations until their SDK slices.
- **Client composition.** A feature's Client Plugin registers its additive contributions through DSH Slots. Each first-party Panel has its own Client Plugin in `panels/<id>/` with a native Loader row and Fiber-owned public Dock registration. Client Plugins inject Client Services and cross the Host boundary through Typert or the existing authenticated Fetch and SSE paths.
- **Host bridge.** Move handlers and feature-specific dependency types out of `methods.ts`. Keep `createBridgeMethods`, the aggregate `BridgeMethods` type and the trusted Human context in the shared adapter. Move feature-specific argument validation and result shaping out of `rpc.ts` where its Typert contract permits it. Assemble the feature adapter slices and their method lists at the shared `BotharnessBridgeService` boundary. Keep the exposed names, parameter and error layouts, descriptor order, stream lifetimes and access gates. Use the same invocation-time Human lookup before dispatch. The DSH API Gateway keeps ownership of `/api`. [Current transport conventions](../../docs/client-bridge.md)
- **Client bridge and copy.** Move calls and presentation adapters to the Client feature folders. Keep shared transport and compatible exports at `bridge.ts`. Use existing `packages/host-client` readers wherever two Clients consume the same shape. Keep `locale.ts` as the namespace and catalogue composition point. Compose feature dictionaries with the same keys and current typing and fallback behavior. Use the same approach for the native English and Chinese dictionaries, preserving live exports of `t` and `useStrings`.

- **Import direction.** A feature can import kernel contracts. Kernel modules depend on narrow Service Definitions and receive Providers from composition. They share neither internal stores nor sibling implementation modules. `plugin.ts` and the schema and bridge composition roots may import feature registrations or manifests. A future rule in `scripts/check-package-boundaries.mjs` can enforce this graph with explicit composition entry points and Service Definition paths. ## Storage Domain finding

The Tobs Host owns one Operational Database. Features and Plugins declare namespaced tables and ordered migrations. The Host validates declarations, applies migrations, and owns Profile Backup, Managed Restore, PersonaBot Deletion and purge. Existing Git-backed Memory Repositories, Profile files, attachment bytes and DSH Session Persistence retain their authorities during H-2. Moving migration definitions preserves current table names and stored data. [Operational Database owner](../../packages/core/src/database/owner.ts), [Profile Backup and Managed Restore](../../packages/core/src/portability/package.ts), [Glossary](../../GLOSSARY.md)

### Open questions for S0

- **Table names.** How does the Host map a feature ID to a safe, unique SQL prefix, reserve shared and first-party namespaces, and retain grandfathered names? If adopting native KV names, how does it prevent ambiguous unit/table concatenations?
- **Migration ownership.** How does the Host validate and order new migrations, constrain writes to declared data, and recover from missing code, version mismatch, interrupted upgrades and cross-feature dependencies? How does S1 cut over old Todo data exactly once, including disabled installations?
- **Lifecycle enumeration.** What durable declarations identify Profile-scoped data, Bot-scoped records and managed files while a Plugin is disabled, uninstalled or incompatible? Which restore and purge steps can run without its code, and when must the Host refuse? Keep explicit Bot share/export opt-ins distinct from Profile Backup membership.
- **KV or documents.** Do small features need a KV API? If so, can a native Storage Domain Provider use the Host connection, transaction, snapshot and purge contracts with explicit limits for keys, records, total size and open-time loading? Specify how version changes and record deletion behave.
