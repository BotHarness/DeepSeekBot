# Team mode M9 lifecycle boundaries

The application-defined `TeamService` owns password, grant and member lifecycle admission for #4147. The existing Typert Service and API Gateway expose the operations; `team/member-methods.ts` remains import-free and is an invocation catalog, never an authorization grant. Every operation checks `members.manage` inside the Service, the caller's current permission ceiling against all target roles (even for inactive targets), Owner protection and self protection. Admin targets require the Owner. Password reset checks again after hashing and removes Owner-issuance provenance when a manager issues the reset.

The integration baseline is main `2d1747902` (M1, M3 and M2). Ordinary private Bots are included in transfer preview and move to the destination Human with their existing Memory and DM history. Both the indexed owner column and retained record ownership change in one transaction. A dedicated `bot-ownership` commit topic refreshes both live rosters after that write. The destination joins groups containing the transferred Bots, preserving M2's owner-membership admission rule. A member's Tob remains bound to that member and is never transferred. Group ownership still requires transfer before purge; remaining private Bots can instead be permanently deleted with the member. Shared Bot visibility and shared roots remain future slices.

M9 is schema generation **144**, following M2's unchanged generation 143. An upgrade test opens a real 143 database containing an existing member, credential, private Bot and Tob identity, then applies 144 and checks identity/ownership preservation and foreign-key integrity. The migration rebuilds the referenced `humans` table through the database owner's staging workflow, expands statuses to `active` / `suspended` / `deactivated`, and adds indexed status lookup, mode restoration records and anonymous deletion markers.

Reset, deactivation and disabling revoke browser grants and use the existing pairing authority to revoke paired devices and close its streams. Peer disposal cancels browser carrier streams. An unavailable pairing authority refuses before a credential/status change when live paired grants exist. Owner grants and Peers remain valid on mode off. Every non-Owner is suspended while mode is off; the first off records whether the member was active or deactivated, and repeated off preserves that record. Re-enabling restores that state without restoring grants. Deactivation and mode off stop all affected Bot/Tob turns through the canonical runtime stop path. M2 execution eligibility additionally compares the captured Bot owner to current Registry ownership, preventing queued work from running under stale authority after transfer. Explicit Bot pause settings stay unchanged; member status is the reversible execution gate. Reactivation revokes stale grants before opening admission. Password changes keep the invocation's current grant and revoke other grants by default. Explicit `signOutOthers: false` preserves others, except during the forced initial change.

`ContentPurge` owns permanent deletion. It issues at most 128 process-local tokens, bound to actor, target and the previewed private-content fingerprint, with five-minute expiry and single-use confirmation. The Team Service independently rechecks current permissions, deactivation, pending transfers and exact username. Content Purge accepts private-source tombstones and a deleted-Human fact together in its durable monotonic ledger. Checkpoint version 3 carries anonymous Human IDs, deletion times, private Bot slugs and private Channel IDs; it contains neither credentials nor names. Replay removes identity and credential records, member grants, membership, read/attention state and paired-device metadata, clears private Channel metadata and rewrites shared-message authors as `{ kind: 'human', humanId, deleted: true }`. Shared message bodies remain. Older snapshots cannot restore a deleted identity; pre-transfer snapshot ownership falls back to the current Owner. Private Bot and Tob deletion is accepted into the existing PersonaBot deletion state by Content Purge. Live confirmation awaits the existing stop/Memory cleanup path; startup replays cleanup serially. Memory ownership, inode, overlap and symlink checks remain mandatory, including for Tob. An unsafe Memory refuses preview with `purge-scope-unsupported`. Completed cleanup scrubs retained private Bot profile text. Existing managed-file reference checks preserve shared attachments and apply private-file cleanup. Failed ledger application fails the operational database closed, with replay required before admission.

Private scope includes Human-owned/exclusive DMs, DMs of the member's Bots and Tob, and local Bot–Bot DMs whose entire Bot audience belongs to that member. Sources placed outside the private scope remain. Purge counts include retained private Bots and Tob, including previously deleted Bots whose Memory still needs erasure. Shared Channel messages remain with anonymous deleted-Human authorship. Browser stream cancellation and paired stream closure use actual DSH Peer/Gateway and actual device pairing in tests; M8 mobile sign-in remains separate.

Deleted-Human ledger facts accept identical replay and reject conflicting duplicates atomically, including conflicts within a single import. Member preview fingerprints the removable managed-file set as well as private content, so a reference appearing or disappearing elsewhere requires a new preview. Author rewrites publish `member-purged` only after their transaction commits and only when identity data changes. The Host refreshes roster/purge subscribers and ends open Channel streams; the existing typed journal carrier repairs its window from canonical messages, including deleted authorship, without treating retained shared messages as redactions. The legacy EventSource fallback receives the post-commit roster signal and stream termination but needs Client-side repair handling to replace cached authors; no Client changes are included here. Publication visits only live subscribers on this cold path; no new per-message query or timer is introduced. DM ownership remains derived from current Bot ownership, so transfer carries the Bot DM to its recipient without an obsolete Human owner stamp.

The configured managed Registry root is created and canonicalized once at Registry initialization. A Profile reached through an ancestor alias (including macOS `/var` → `/private/var`) therefore records Memory ownership against the real path. The first-sign-in regression uses actual member creation and `TeamService.signIn`, rather than seeded credentials and a direct Tob call, under an aliased Profile. It covers Tob-only purge, transfer of an ordinary private Bot before purge, and a member who never signed in. Symlinks below the canonical root, changed repository identities, unproven custom directories and invalid retained ownership proofs remain refused. Previously recorded invalid proofs are not silently adopted. Canonicalizing the root adds one directory ensure and one path resolution at startup; no message, admission or preview loop gains filesystem work.

## Wire contract for the Client

All payloads use Human IDs. Existing password errors (`credentials-invalid`, `password-weak`, `password-reused`, `password-change-required`, `rate-limited`) remain. Invalid payloads use `invalid-input`. Management refusals are `permission-required` with `details.permission`, `permission-not-grantable` with `details.permission`, `owner-protected` and `member-not-found`. Self and Admin protection use `permission-required` with `details.permission: 'owner'`.

| Method                  | Payload                                      | Success                                                                                               |
| ----------------------- | -------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `memberPasswordReset`   | `{ humanId }`                                | `{ initialPassword }` (one-time reveal)                                                               |
| `memberPasswordChange`  | `{ current, next, signOutOthers?: boolean }` | `null`; default `true`                                                                                |
| `teamMode`              | `{}`                                         | Existing view plus `activeMembers`                                                                    |
| `teamModeSet`           | `{ enabled: boolean }`                       | View plus `suspendedMembers` (count active before off; zero on on/no new active members)              |
| `memberDeactivate`      | `{ humanId }`                                | `null`                                                                                                |
| `memberReactivate`      | `{ humanId }`                                | `null`; mode off: `team-mode-off`                                                                     |
| `memberTransferPreview` | `{ humanId }`                                | `{ channels: [{ channelId, name }], bots: [{ slug, displayName }] }`                                  |
| `memberTransfer`        | `{ humanId, toHumanId }`                     | `null`; missing destination: `member-not-found`; self/inactive destination: `transfer-target-invalid` |
| `memberPurgePreview`    | `{ humanId }`                                | `{ token, counts: { channels, bots, messages, files } }`                                              |
| `memberPurgeConfirm`    | `{ humanId, token, username }`               | `null`                                                                                                |

Both purge methods return `member-active` unless deactivated, and `transfer-required` while group ownership remains. Ordinary private Bots may be transferred or erased; Tob is erased on member purge. Confirmation returns `purge-token-invalid` for an incorrect username, token, actor, target, changed private scope, expired token or reused token. Content Purge failures retain `purge-unavailable`. Tokens expire on Host restart. Directory status adds `deactivated`; mode suspension remains `suspended`. The UI owns labels, dialogs, password reveal, translations and deleted-author rendering. No Client or mobile code changes belong to this logic branch.

## Performance and verification

No dependency, background worker or timer is added. Argon2 retains the existing bounded queue. `teamMode` adds one indexed active-member count; directory and effective-permission query budgets stay unchanged at 1,003 Humans. Revocation scales with the target's live grants/devices, not all Host content. Purge preview/confirmation is explicit cold-path work; it selects private sources through SQL, fingerprints the selected content and uses existing managed-reference scans and ledger application. Tokens are bounded at 128 and expiration cleanup runs on preview requests. Bot selection uses M2's ownership index, stop work scales with the affected Bots, and startup Memory cleanup is serial. Pending cleanup promises are removed on settlement. Runtime eligibility uses one Registry point lookup and one indexed Human/settings SQL query; it never lists the Host roster. Tests cover these resource bounds and role/refusal semantics independently of timing; no end-to-end performance gain is claimed.
