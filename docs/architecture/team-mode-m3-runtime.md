# Team mode M3 runtime boundaries

This records the application-defined Host/CLI half of #4142, stacked on [M1](team-mode-m1-runtime.md). `TeamRoles` owns role queries and mutations through the operational database; `TeamService` owns credentials, grants and transfer. The existing BotHarness Typert Service and API Gateway remain the only invocation path. No member operation mints or forwards an Owner cookie.

Schema generation 142 adds `host_roles`, `human_roles` and `team_settings.owner_human_id`. Existing M1 members receive `member`; `local-human` initially remains Owner. Owner authority is separate from Human identity and authorship. A transfer removes the incoming Owner's assignments and gives the outgoing Owner `admin` in the same transaction. Local Owner invocations resolve the current pointer. The local OS authority remains trusted. Members, including an Owner using the member carrier, retain the DSH-native default denial.

The fixed 15-permission catalog is code-defined. Owner permissions are implicit. Member permissions are the union of current role permissions. Admin cannot contain `privateContent.view`; only the Owner may put it into custom roles or assign those roles, with private-content access enforcement deferred to M11. Only the Owner can assign the built-in `admin`, including during member creation. Non-Owners can delegate only permissions they currently hold, cannot edit or delete roles beyond that ceiling, and cannot change their own role assignments. Role deletion also checks any automatic Member fallback against the delegation ceiling. Empty role assignments and deletion of the last assigned role fall back to `member`. Names are trimmed, bounded to 128 code units, and unique under SQLite NOCASE collation. Built-in ids remain stable when their names change.

Management checks execute inside the owning Service on every call so refusals retain `permission-required` and `details.permission`. Either `roles.manage` or `members.manage` admits role listing; writes require their corresponding permission. The import-free member-method catalog declares callable endpoints, not permission grants. Mutations invalidate `remoteAccess` snapshots. Member creation rechecks authority and the delegation ceiling after password hashing yields. Delegation checks load the caller ceiling once per synchronous mutation and compare permissions in memory; existing query budgets for reads remain unchanged. Owner transfer rechecks both authority and credential version after password verification. M1 password recovery (`memberPasswordReset`) stays Owner-only, protects the current Owner after transfer, and rechecks caller authority and target protection after hashing.

`memberDevices` returns only active browser and paired-device grants for the authorized target. Self access requires no directory permission. `current` comes from the invocation principal, never payload. Browser grants have an empty label until a later device-label flow supplies one; Clients own the fallback label. Browser revocation disposes the exact Peer. Paired-device revocation calls the existing pairing authority, closing streams and invoking push/call/video cleanup. Transfers revoke the outgoing Owner's paired-device grants; old pairing offers cannot redeem into the new Owner. Fresh Owner pairing binds the current Owner's Human ID. Member self-pairing remains M8.

The CLI resolves self `devices --member` from `teamMode` under `--as`, without listing members. Other username operations use the permission-checked member directory. Initial passwords go only to new private files; ownership transfer passwords require stdin and explicit confirmation. `roles catalog` exposes catalog ids and groups without labels.

Performance guard: effective permissions use one indexed query; the member and role directories each use two reads including permission admission, with no per-row query loop. Tests retain those budgets with 1,003 Humans. Role assignment and grant counts use existing primary keys plus the role-side index. Role mutations do not add timers, resident workers or dependencies. Password hashing retains M1's bounded worker queue. Real Host/CLI evidence, rendered Client behavior, installed native behavior and Human acceptance remain separate qualifications.

Permissions for later Bot, DM, model, IM, Workspace, approval, usage, audit and private-content slices are stored without enabling those endpoints. Channel visibility/admin semantics remain owned by M4; M3 applies `team.settings` to public flags and Team settings.

A task-local M1/M3 query benchmark used the same 1,003-Human database and three interleaved 300-call samples per side. Member admission was 0.30–0.89 ms before and 0.37–0.61 ms after; Owner status was 0.27–0.47 ms before and 1.25–1.39 ms after (six reads after). Public Channel browse retained one read. Added effective-permission lookup measured 0.70 ms and one read. Concurrent machine load produced substantial timing variation; these are SQLite/Service diagnostics, not end-to-end latency or a speedup claim. The regression guard asserts query counts independently of timing.

Review hardening in #4164 keeps suspended Humans out of effective permissions and requires CLI confirmation for role deletion. The Core owns the canonical `TeamService` and supplies a current-Owner predicate to all live visibility gates; queued roster and Channel frames recheck it at delivery. Owner transfer supersedes every pending pairing offer, so an A→B→A round trip cannot revive a bearer offer. Owner checks use an indexed singleton lookup, with no new timers or background workers.

The [Owner-transfer credential rule](team-mode.md#m3-owner-transfer-credential-rule) stores optional `ownerIssuerHumanId` beside the current hash in the existing password JSON. Hash parameters and credential history remain unchanged. Legacy or member-manager credentials fail transfer eligibility until current-Owner reset and completed forced change. The transfer payload and schema generation 142 remain unchanged; Clients need to map `owner-transfer-target-unverified` to that recovery path.
