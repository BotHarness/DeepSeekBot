# Team mode M11 runtime boundaries

This is the application-defined Host/CLI half of #4149 under ADR-0336. The existing BotHarness Typert Service and API Gateway carry every invocation. `TeamPrivateContent`, owned by `TeamService`, enforces current Human permissions; `PrivateAudit` owns the durable SQLite access chain. No native DSH API or second authentication authority is introduced.

## Wire contract

| Method               | Payload                       | Result                                       |
| -------------------- | ----------------------------- | -------------------------------------------- |
| `privateObjects`     | `{ humanId?, kind? }`         | `PrivateObject[]`                            |
| `privateContentOpen` | `{ kind, objectId, reason? }` | `{ viewId, object, messages, memoryFiles? }` |
| `privateContentPage` | `{ viewId, before }`          | `{ messages }`                               |
| `auditLog`           | `{ after?, limit? }`          | `{ records, next? }`                         |
| `auditVerify`        | `{}`                          | `{ ok: true }` or `{ ok: false, brokenAt }`  |

`kind` is `bot`, `channel`, `dm` or `bot-dm`. Private-object listings contain only `{ objectId, kind, name, ownerHumanIds, ownerNames }`. `ownerNames` contains current Human display names in `ownerHumanIds` order, with an empty string for a missing Human; usernames are never used as a fallback. Names are fetched in one batched query after permission/ownership filtering, so the picker needs only `privateContent.view`, without `members.manage`. The existing granting ceiling still applies. Open-view object metadata retains `{ objectId, kind, name, ownerHumanIds }`. Bot IDs are slugs; all other IDs are Channel IDs. Human–Bot and Human–Human DMs use `dm`; local Bot–Bot DMs use `bot-dm`. Remote Bot DMs, deleted objects and public/role Channels are excluded. Existing legitimate readers of a private Channel and participating DM owners use their ordinary read path: an audited open returns `own-content`.

Bot opens add the canonical Bot record as `object.profile` and its `object.profileFingerprint`. Full profile fields are available only inside this audited response for another Human’s Bot. `memoryFiles` contains the existing Memory read representation (`path`, `body`, `head`, and optional Markdown/image/binary metadata). Bot messages come from its Human DM; Bot–Bot DMs remain separate objects. Every message page contains at most 50 messages, newest first; pass the oldest returned message ID as `before`. No mutation operation is exposed.

For CLI username resolution, `privateObjects` additionally accepts `username?`, mutually exclusive with `humanId`. Resolution happens inside the permission-checked Service and does not require `members.manage`. Unknown usernames return `object-not-found`.

`privateContent.view` admits object discovery/open/page; `audit.view` admits log/verify. The Owner has implicit permissions. Non-Owner viewers cannot inspect the Owner or an object owner whose role permissions exceed their own ceiling. Lists omit these targets; open/page return `permission-required` with `details.permission: 'privateContent.view'`. Own content returns `own-content` without recording access. Bot-origin contexts refuse every method, even with an Owner or holder Human ID; the Owner Tob CLI broker refuses `audit` and `private` before execution or approval. These methods are not Bot tools.

Views hold metadata only, bind the Human ID, expire after 30 minutes without renewal and disappear on Host restart. A view is registered only after all initial content loads successfully; failed provider reads retain the access-attempt audit record but consume no view slot. DM ownership includes historical Bot records, so retained DMs keep every owner and cannot bypass the Owner/permission ceiling after a Bot deletion. The process retains at most 128 views; capacity returns `private-views-full`. Expired, foreign, removed or ownership-changed views return `object-not-found`. Every page rechecks permissions and object ownership. Role revocation clears views, disposes existing browser Peers, closes the paired-device mux and invalidates current access through the established M3/M4 revocation path.

## Durable audit

Each open commits one record before reading private content; list and page do not append. Consequently a downstream Memory read failure can still leave the truthful access-attempt record. Records retain names and Human IDs independently of subsequent offboarding. They contain no message bodies, Memory content or credentials. Optional reasons are trimmed and limited to 1,024 code units.

`private_access_audit` has monotonic sequence order and a unique `audit_id`. `record_json` contains the specified record, with SHA-256 over the schema-ordered unsigned JSON, including the prior hash. `private_audit_head` retains the last sequence, audit ID and hash in the same transaction. Verification checks sequence continuity, every digest/link, the row identity and the durable head. The head detects tail deletion or deletion of all audit rows, as well as interior deletion and edits. Append refuses a damaged tail with `audit-integrity-failed`; it never resets the chain. This is tamper evidence against independent row changes, not an external signature against a database administrator rewriting both chain and head.

Audit pages are oldest first. `after` and `next` are audit IDs; default `limit` is 50, maximum 200. Invalid limits, cursors or payloads return `invalid-input`. No edit, delete or reset RPC/CLI exists.

The migration derives its generation from the preceding M6 `WORKSPACE_SPACES_MIGRATION`: 151 → **152**, after M10 models/usage 148–149 and Account enrollment 150. Upgrade coverage includes a generation-151 database and restart. The import-free `member-methods.ts` preserves M6 Workspace and approval methods alongside M11’s five methods. Recheck the final preceding generation at integration; do not ship duplicates or move an already published migration.

## CLI and Client handoff

Commands are `audit list [--after <auditId>] [--limit <1..200>]`, `audit verify`, `private list [--member <username>] [--kind <kind>]`, `private open <kind> <id> [--reason <text>]`, and `private page <viewId> --before <messageId>`. Every command supports `--as` and dispatches through the same Gateway and Service. Stdout is one JSON document: the result on success, `{ error: { code, message, details? } }` on refusal.

`teamMode` adds `privateAccessNotice: true` while Team mode is enabled and omits it otherwise. Client/mobile surfaces, translated labels/notices, bilingual CLI guide copy and the combined feature's bilingual release fragment belong to the UI integration. The UI must display the audited-view banner before opening/reading, retain `viewId` across pagination, expose no writes and map the coded refusals above. Rendered, installed native and Human acceptance remain separate from Host/CLI verification.

## Legacy Bot administration

Owner reads of another Human’s Bot through `get`, `modelPlan` and `deletionMemoryFolder` return `{ metadataOnly: true, bot: { slug, displayName, ownerHumanId, owner: false, paused, createdAt } }`. They do not load private Memory or append audit records. `list({ administration: true })` uses that same Bot metadata for foreign Bots and matches queries only against slug/display name. Own Bot responses are unchanged. This applies to the Gateway and CLI, including `--as` with the Owner username; an open view never changes the legacy read response. Legacy Memory CLI commands now route `--as` to the member Gateway; its existing default-deny policy for Memory/prompt endpoints remains intact (`remote-access/denied`, including the Owner on that carrier). Offline `show` also returns metadata; offline private Memory/model reads and settings mutations are refused through the scoped Registry.

`deletionPreview` adds only `preview: { slug, displayName, token, eraseAvailable, deletion? }`. Successful deletion confirmation/retry adds only `deletion: { slug, displayName, acceptedAt, eraseMemory, phase, memory }`; the optional preview deletion has the same shape. Dependencies, Session IDs, paths and failure details are omitted. Other administrative mutations return the metadata result. Full profile, Memory and DM reads require `privateContentOpen`; existing private prompt/message endpoints remain refused.

Before cross-owner administrative effects, the Service appends a `kind: 'bot'` record with `action` equal to the bridge method name. Supported direct actions are `update`, `pause`, `resume`, `deletionConfirm`, `deletionRetry`, `botAvatarSet`, `botAppearanceSet`, `botBannerSet`, `botPrimaryColorSet`, `modelPlanSet`, `modelPresetApply`, `modelPlanCustomize`, `modelPlanAssignmentsSet`, `standingLimitsSet` and `modelPlanInherit`. Member transfer/purge append one record per affected Bot with `transfer` or `memberPurgeConfirm`, preserving its original owner. Management ceilings remain enforced. Direct management and purge records describe attempts: downstream validation/effect failure can leave a record, while an audit append failure prevents the effect. Transfer records instead commit atomically with Bot/Channel ownership, Workspace Grant revocation and the M6 filesystem journal. A pre-commit failure rolls back both ownership and the audit rows, then restores prepared filesystem moves; a post-commit interruption retains the rows and committed destinations, closes Peers/streams and permits M6 cleanup recovery. The chain is never edited to compensate for rollback. This composition adds no separate transaction per transferred Bot. Sanitized administrative refusals retain only the contract’s `details.route` for `model-not-allowed` or `details.permission` for `permission-required`. Own Bot management does not append. `action` is absent on viewing records and optional in the schema; existing record hashes remain valid. No additional migration is needed beyond M11 generation 152.

Bot-origin bridge administration is refused before reading or effects. Tob profile/model operations enforce current Bot ownership; the common dispatcher and Host CLI runner recheck targets before execution, including after approval. Tob cannot forward `--as` or `--administration`, or execute member transfer/purge. Member actions are parsed with the Human CLI’s shared option catalog before this denial, including intervening flags and option values. Group creation checks every `members` entry before preparation and again after approval; this is the only list of Bot inputs on that operation path, and the existing 100-member limit bounds its lookups. Human administration remains available through the audited online Host path.

## Performance

No dependency, worker, polling loop or timer is added. Ordinary message admission and reads do not query the audit. Existing Team status gains only the notice field, with no additional query. Discovery is an explicit metadata inventory, with batched membership and ceiling reads. Open/page use point lookups rather than listing the Host roster or Channels; message pages stay at 50. Appending hashes one bounded record and reads only the tail/head; audit list uses indexed sequence/cursor reads. Administrative metadata reads skip private Memory IO. Administrative writes add one bounded append per affected foreign Bot; no ordinary message hot path is changed. Tests assert metadata reads do not call the Memory reader and audit failure prevents effects. Full verification is an explicit streaming O(records) operation. Bot opens additionally perform the existing Memory snapshot/file reads, proportional to that Bot's Memory. Regression tests guard page size, absence of inventory reads on open/page, bounded view state and existing Team query budgets. Measurements are Host/CLI diagnostics, not browser or native performance claims.
