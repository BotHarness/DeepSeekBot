# M13 minimal Member and Owner Tob logic

Issue #4187 and the 2026-11-15 amendment of #4137 supersede M2's per-member Tob and M3's broad Member defaults. This is the Host/CLI half; Client, mobile and Human acceptance belong to the UI integration.

The application-defined Team Service's catalog replaces `bots.create` with `bots.createPrivate` and `bots.createPublic`, both in group `bots`. Member grants exactly `dm.humans`. `bots.createPublic` is catalogued and grantable under M3's normal permission ceilings; M7 owns publication enforcement. Channel creation still requires `channels.create` and model selection still requires `models.use`.

Every member creation/import invocation first checks `bots.createPrivate` at the existing Human bridge Service entrance, including cached `createLookup`, Git lookup/preview, ZIP upload/import and Marketplace installation. A missing grant returns `permission-required` with `details.permission: 'bots.createPrivate'` before validation, reservation, disk or network work. The grant enables blank creation and private Git/ZIP/Marketplace imports, including Marketplace review. Import Services bind ownership to the authenticated Human, namespace operation receipts and ZIP upload keys by Human, and recheck current permission before an asynchronous import commits. Imported descriptors cannot select an owner, Workspace, Memory path or audience. M6 supplies the same caller account Memory and read/write files Grant as blank creation; M11 keeps foreign private content unavailable. Receipts stop resolving when a Bot transfers to another Human. Explicit public creation/import requests require `bots.createPublic` and then refuse with `invalid-input` until M7 provides publication; they never silently become private imports. `team/member-methods.ts` remains import-free.

`tobHome {}` returns `{ available: false }` for a member, without a slug, Channel, Workspace or attention fields. It succeeds even when the optional Tob Service is absent. Owner success keeps the existing `{ botSlug, channelId, workspacePath, attention? }` shape without an added discriminator. Member `onboarding` succeeds with `{ profileId: humanId, tutorial: 'skipped', completed: true, preparation: 'ready' }`, without `defaultBotSlug` or `channelId`. Neither path allocates a Bot, DM, Memory or Workspace. Sign-in calls Tob preparation only for the current Owner. The Tob Service independently refuses non-Owners with `tob-unavailable`, follows the current Owner after transfer, and rechecks that authority after asynchronous Workspace preparation.

The migration is appended at the next generation computed from the integrated base plan, currently **153** after same-account provenance (150), M6 Workspace spaces (151), and M11 private-content audit (152). Their published generations remain unchanged; M13 still computes `max(BASE_MIGRATIONS) + 1`. An unchanged legacy Member has the original name, complete four-permission set and all-model policy. Only that role is narrowed. Changed Member names, permissions or model policies are retained. Every legacy `bots.create` grant maps to `bots.createPrivate`, including custom roles, with duplicates removed.

The migration removes non-Owner rows from `tob_identity` only. It leaves Bot records, ownership, Memory, DMs, Workspace Grants and usage untouched. Former member Tobs are ordinary private Bots: they can be deleted, added to groups and transferred under the existing owner rules. Only the current Owner's identity is protected by `isTob`. Ownership transfer atomically retires the demoted Owner's identity without changing their Bot or data. It also clears a stale target identity left by an earlier build. A later promotion allocates a fresh Tob, even if that former Tob has transferred to someone else. M9 lifecycle and M10 usage tests cover members with zero Bots and retained former Tobs. M6 relocation discovers registered legacy Tob Workspace paths and active Grants from the canonical Bot record and its current owner, independently of `tob_identity`. Thus removing the member Tob identity cannot suppress pending file relocation. The existing Memory move queue still places member repositories in their account space before Workspace files move; inode/copy proofs, collision checks, link containment and transactional rollback remain unchanged. Grant-only registrations are included without adding a root Workspace. Each active legacy Grant maps to its original relative subpath under the account files root, preserving its own write flag; lexical and canonical containment are checked before and after moving files. Revoked destination Grants are never restored, and a completed relocation is a two-read no-op on subsequent starts. Tests cover upgrades from 147/149/150 and interrupted post-schema 151/152 startup, nested Memory repositories, byte/Git-history preservation, and transfer/purge with an ordinary former Tob. Every sign-in ensures the account directory even when the member has no Tob or Bots.

CLI uses the existing online commands: `roles catalog`, `--as <username> bots create`, `--as <username> tob-home` and `--as <username> onboarding`. The unwrapped no-Tob success is `{ available: false }`; the Client/CLI presentation can describe it as no Tob. Grant-based imports also use the existing `--as <username> bot-zip-upload`, `bot-zip-import`, `bot-zip-import-status`, Git import and Marketplace commands. The live smoke covers refusal before the grant, private import/retry with the grant and refusal after revocation. No Owner cookie is minted for member traffic. Permission removal continues through M3's existing invalidation, browser Peer disposal and paired-device stream closure; the same method table checks current permissions on every invocation.

Performance: no dependency, worker, timer or message-path work is added. Member sign-in removes filesystem/Git/Workspace preparation. No-Tob home admission has a fixed three database reads, independent of roster size, and creation refusal has two indexed reads before side effects. Existing M2 ownership-index, M3 directory/permission and device revocation budgets remain guards. Import namespace hashing is constant per request; no import file or network work runs before the permission check. Owner transfer clears the two indexed identity keys in its existing transaction. Migration scans roles once on the cold upgrade path and deletes only indexed identity rows; no per-message scan is introduced. These bounds do not claim end-to-end latency gains.

The UI integration must add the two permission labels, gate Create Bot and Create channel with their respective grants, handle the no-Tob union, suppress Tob onboarding/entry points, and show Browse channels when a member has no Channels, including a Team-mode remote Host. M7 adds shared-Bot discovery. The bilingual release fragment and public CLI guide copy remain with the UI owner under this task's copy boundary.
