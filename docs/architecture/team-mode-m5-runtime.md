# Team mode M5 logic boundary

The application-defined `TeamApprovals` service evaluates current Human status, Bot ownership and Host Role permissions. The existing `approvals.opaqueTools` permission supplies the additional approver role (Owner/Admin by default); membership of a shared Channel alone gives no decision authority. Bot owners can answer their Bot's ordinary questions and secret requests. An opaque DSH tool request from a member-owned Bot additionally requires `approvals.opaqueTools`, including when its own owner decides. An additional approver must be an active member of the request's Channel. The Bot owner can open and decide their own request from Activity without obtaining the rest of that Channel's history when they satisfy its role and Human-DM audience restrictions. An unattended request outside that audience still reaches the Bot owner's Activity and push as masked metadata; decisions remain refused with `approval-not-allowed`.

Approval controllers depend on the narrow `ApprovalAuthority` contract, while shared card types do not import the concrete Host service. This keeps the mobile type graph out of Host subprocess execution.

The canonical request and decision remain Channel messages backed by Source Events. Timed question submissions record the Human ID and an answer fingerprint as an application-owned `questionAnswerSubmission` Source Event before native delivery. These handled system facts have no Channel placement, message body or Bot Inbox admission. Withdrawals append another fact; an indexed receipt-identity range selects the latest fact. The adapter also reads legacy `plugin:botharness/question-answer` Session receipts structurally. It does not compare or write native `Session` class instances: an isolated CLI can load a different copy of the SDK from the Plugin. Recovery restores the matching actor; a legacy native answer with no matching receipt creates a system-authored resolution without `decidedBy`, never a fabricated Owner decision. No database migration is needed. Tool decisions, question resolutions and private-input resolutions persist `decidedBy: { humanId, displayName? }`. Ordinary request fields remain optional on the message wire type.

Every Human-authored append, including generated resolutions, derives `author: { kind: 'human', humanId, displayName }` from the trusted acting Human and the Host name store. Supplied author IDs cannot impersonate another Human. Takeover completion/cancellation and private-account revocation carry the invocation Human into their writer. A name change does not change message retry identity. Historical envelopes missing Human metadata are repaired in projections from the canonical Source Event `human_id`; deleted-Human tombstones remain anonymous. No migration or historical message rewrite is needed.

Every projected message and Activity item adds an `approval` property:

```ts
// Non-approver: this is the entire approval value.
{ masked: true, kind: 'tool-approval' | 'user-question' | 'private-input',
  botSlug, state, requestedAt, decidedAt? }

// Approver: the existing request/resolution fields remain present.
{ masked: false, kind, botSlug, state, requestedAt, decidedAt?,
  opaque: boolean, decidedBy?: { humanId, displayName? } }
```

For a masked message, each existing request field (`toolApprovalRequest`, `userQuestionRequest`, `privateInputRequest`) is replaced by the entire masked value above. Resolution fields, body contents, attachments, reply previews and other content are removed; the original message ID, timestamp and placement remain. `body` is empty. A masked Activity item has an empty `summary`. A masked search hit has an empty `snippet`. Status responses retain their existing `status` shape and add `approval`. The CLI name `ask-secret-status` maps to `privateInputStatus`; secret answers use `privateInputSubmit` and `privateInputCancel`. Push data carries the same `approval` metadata and omits content previews and interactive approval categories for masked recipients.

Bridge reads and the native Channel stream project on each response/frame, with no cross-request permission cache. The Activity query uses active Channel membership and effective approval permissions independently of private Bot visibility. If no active approver belongs to the Channel, the Bot owner's Activity includes the canonical request. It reuses its existing item ID and push delivery ledger rather than copying the request or creating a second lifecycle. Grant revocation and Peer/stream disposal remain owned by M1/M3/M9.

Channel message authors expose only `{ kind: 'bot', slug, displayName }` for a known Bot, including private Bots absent from the viewer's Bot list. This applies to message pages, timeline, journal, streams, search and roster previews, with the same `author` on message-backed Activity items and push data. Push `sender` uses that display name. Masked approvals retain this author envelope while withholding their content. The Host selects only the name from the canonical Bot record; persona, prompts, Memory and settings remain private. Inline avatar data is not repeated in these envelopes.

Decision failures are codes: `approval-not-allowed`, or `permission-required` with `details.permission: 'approvals.opaqueTools'` for a member-owned opaque tool. The dangerous Assignment preset refuses non-Owners with `owner-only`; a member Bot refuses dangerous access even when configured by the Host Owner with `permission-required`. The store, Assignment snapshot creation, Session admission and per-tool execution enforce the same restriction. Member Sessions require explicit `ask`, never full access or escalation; delegated Sessions are covered by their durable root owner.

`teamMode` and member creation/invitation responses add `isolation: 'trial' | 'enforced'`. This implementation returns `trial`; M12 owns the transition. The server passes `isolation` to `renderTeamSignInPage`, and the sign-in JSON includes `isolation`. UI text and card rendering are delivered separately by Claude. No database migration is needed: existing permission records and canonical message JSON retain the added facts. Main was generation 145 and the visible parallel M4 branch used 146 when this task started.

Performance impact is on Host projection, not rendering: Bot author names add one indexed lookup per distinct Bot within a response; complete Human envelopes perform zero projection reads. Human appends use one indexed identity lookup. Historical Human envelopes use one indexed identity lookup per distinct message within a response. Repeated copies of the same approval share one lookup within a response, and permissions are refreshed on every response/frame. The M5 regression suite bounds these reads, including 200 repeated messages. Existing resolution expression indexes are reused; no dependency, polling loop or timer is added.

Text predicates for Channel search, global message search and every Activity category evaluate the same approval projection before pagination. Non-approvers match only visible approval metadata, including Bot slug and state; hidden body, answer, attachment and Channel-name text cannot select a masked item. Global search retains its FTS candidate path for ordinary content and separately considers approval metadata. Reply previews are removed when their target is masked, missing or purged. Buffered request/resolution bodies are removed when canonical approval facts are unavailable. Search adds projection work only when a text filter is supplied; Activity memoization is bounded to 64 entries and reply-target/card lookups are shared within a projection.

Unexpected answer failures emit bounded `botharness.channel_question.answer_failed` diagnostics with method, phase, error kind, request/Session IDs and function frames. Payloads and exception messages are excluded. The same logging covers member-carrier and Owner calls, and a failed receipt commit leaves the card retryable.
