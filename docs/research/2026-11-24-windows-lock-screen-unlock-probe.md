# Windows lock-screen capture and unlock research

2026-11-24 · [Research #5141](https://github.com/BotHarness/DeepSeekBot/issues/5141) · [Parent spec #5134](https://github.com/BotHarness/DeepSeekBot/issues/5134) · [Android delivery #5143](https://github.com/BotHarness/DeepSeekBot/issues/5143)

**Recommendation.** Keep Windows phone unlock unavailable until there is a supported sign-in design and evidence that it unlocks the same console session. Microsoft documents privileged secure-desktop capture through DXGI Desktop Duplication. The public contracts for synthetic input and UI Automation leave Windows sign-in field delivery unverified. Review the Windows Credential Provider extension point if saved-password unlock remains a requirement for #5143.

**Evidence.** This note uses Microsoft API and policy documentation and Cindy source pinned to a commit. The primary PC stayed in use. There was no locked-screen run, privileged probe, service install, policy change, credential entry, or installer execution. Capture, credential-field delivery, actual unlock, and installer prompts have no local measurements. This research changes no runtime path or dependency, so a performance benchmark does not apply.

## 1. Can LocalSystem capture the console lock screen?

Microsoft documents the Winlogon desktop as accessible to a restricted set of accounts that includes LocalSystem. The DXGI `DuplicateOutput` contract explicitly identifies LocalSystem as the privilege required for secure-desktop access. This makes Desktop Duplication the documented capture candidate. It does not establish that the proposed worker obtains a usable image on a given Windows 11 build, GPU, display configuration, or lock-screen presentation. DXGI separately documents loss of the duplication interface on desktop switches. [Win32 desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops) · [DuplicateOutput](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutput1-duplicateoutput) · [AcquireNextFrame](https://learn.microsoft.com/en-us/windows/win32/api/dxgi1_2/nf-dxgi1_2-idxgioutputduplication-acquirenextframe)

Service identity and console session are separate facts. A service in Session 0 cannot directly interact with the user's desktop. `WTSGetActiveConsoleSessionId` identifies the physical console session and may report that no session is attached during a transition. Treat general-purpose screen capture, an earlier unlocked frame, and an image from any other session as insufficient evidence. Windows Graphics Capture documents user-selected display or window capture and the possibility of blocked capture. That contract supplies no assurance for the protected Winlogon surface. [Interactive services](https://learn.microsoft.com/en-us/windows/win32/services/interactive-services) · [Console session ID](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-wtsgetactiveconsolesessionid) · [Windows Graphics Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture)

## 2. Can SendInput or UI Automation fill a field and unlock it?

**Unverified.** `SendInput` inserts events into an input stream and is subject to User Interface Privilege Isolation (UIPI). Its return value counts accepted events. It does not identify the receiving control or prove that an event changed the field. UIPI blocking is also indistinguishable from other failures by the return value and last error alone. An ordinary unlocked application can exercise input plumbing but supplies no evidence about LogonUI. [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput)

UI Automation defines `IsPassword` metadata and a generic `ValuePattern.SetValue` operation on suitable writable controls. The generic edit-control contract neither promises a writable value pattern for every Windows sign-in tile nor permits password readback as evidence. LocalSystem desktop access alone does not establish either input path. Microsoft documents Credential Providers as the extension point for sign-in. Providers gather and serialize credentials, and Windows authentication packages apply policy and authorize them. A custom provider has its own deployment and recovery risks. Microsoft recommends retaining a system credential provider and discourages wrapping existing providers because Windows updates can break the wrapper. [UI Automation edit controls](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-supporteditcontroltype) · [ValuePattern.SetValue](https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomationvaluepattern-setvalue) · [Windows Credential Providers](https://learn.microsoft.com/en-us/windows/win32/secauthn/credential-providers-in-windows)

A visible masked field change with a cleared dummy value would establish field delivery only. Actual unlock requires Windows to report an unlock for the intended session after the attempt starts, followed by a fresh session-state check confirming that the same account's desktop is unlocked. A disconnected or newly attached console, an account switch, disappearance of a dialog, and successful credential validation alone cannot establish that result. The Human's local sign-in can validate the observer but cannot establish that a phone transaction caused the transition. [Session change notifications](https://learn.microsoft.com/en-us/windows/win32/termserv/wm-wtssession-change) · [WTS session lock state](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/ns-wtsapi32-wtsinfoex_level1_w)

## 3. Is Ctrl+Alt+Del required with existing policy?

Two settings answer different questions. **Interactive logon: Do not require Ctrl+Alt+Del** determines whether Windows requires a secure attention sequence (SAS). **SoftwareSASGeneration** determines who may generate it in software. Microsoft documents `SendSAS` as policy-gated with no return value. Advancing to the intended sign-in screen is the evidence that the SAS gate was satisfied. [Interactive logon policy](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/security-policy-settings/interactive-logon-do-not-require-ctrl-alt-del) · [SoftwareSASGeneration](https://learn.microsoft.com/en-us/windows/client-management/mdm/policy-csp-admx-winlogon#softwaresasgeneration) · [SendSAS](https://learn.microsoft.com/en-us/windows/win32/api/sas/nf-sas-sendsas)

| Existing settings                                                                               | Consequence                                                                                                                 |
| ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| Windows does not require SAS                                                                    | SAS adds no prerequisite. Reaching and using the expected sign-in screen still needs evidence.                              |
| Windows requires SAS and policy allows services to generate it                                  | Windows documents service eligibility. The target session must still be observed advancing.                                 |
| Windows requires SAS and software SAS is denied, limited to accessibility apps, or unconfigured | A service cannot satisfy the gate under that policy. Require local Human action or report Windows phone unlock unavailable. |

Keep both settings intact. Cindy's Windows service calls `SendSAS` and leaves permission to Windows policy. Its native README leaves Windows lock and UAC behavior to release validation, and its automatic-unlock documentation lists macOS and supported Linux lock screens as targets. This is a precedent for respecting policy and evidence limits. It supplies no Windows credential-field or automatic-unlock result. The upstream code is Apache-2.0. This note uses it as a reference. [Cindy service](https://github.com/makecindy/cindy/blob/42248355252b8af7aad2169dd764b3fede8b1b34/apps/desktop/native/remote-desktop/windows-host/src/service.rs) · [Native README](https://github.com/makecindy/cindy/blob/42248355252b8af7aad2169dd764b3fede8b1b34/apps/desktop/native/remote-desktop/README.md) · [Automatic unlock](https://github.com/makecindy/cindy/blob/42248355252b8af7aad2169dd764b3fede8b1b34/docs/remote-desktop-credentials.md) · [License](https://github.com/makecindy/cindy/blob/42248355252b8af7aad2169dd764b3fede8b1b34/LICENSE)

## 4. How do password, PIN, and account type differ?

Windows selects available sign-in methods through its credential providers. A Windows Hello PIN is tied to the Windows device. Hello for a Microsoft account can use key-based authentication, while Microsoft describes local-account Hello as a convenience sign-in without the same asymmetric key protection. A Microsoft account can also have password sign-in disabled on that device by the Hello-only setting. These are documented differences in eligibility. All four combinations remain untested for Windows phone unlock. [Windows sign-in options](https://support.microsoft.com/en-us/accounts-billing/security/sign-in-options-in-windows) · [Windows Hello overview](https://learn.microsoft.com/en-us/windows/security/identity-protection/hello-for-business/hello-why-pin-is-better-than-password)

| Account and credential                  | Scope for #5143                                                                                                                                 |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Local account and password              | First candidate if Windows offers a password tile for the locked account. Keep account matching explicit even if the display name looks unique. |
| Microsoft account and password          | Separate qualification. Refuse when the password provider is unavailable, including on Hello-only setups.                                       |
| Local account and Windows Hello PIN     | Defer. Requires separate review and qualification for a device-bound sign-in method.                                                            |
| Microsoft account and Windows Hello PIN | Defer. Qualify the device, account, and enabled provider together if the scope expands.                                                         |

Microsoft documents that Windows can use a combined logon and workstation-unlock scenario or a distinct unlock scenario depending on policy. This is another reason to bind results to the existing session and account rather than inferring them from the selected tile. Keep Windows Hello recovery, first sign-in after boot, switch-user, and work or school accounts out of the first qualification. [Credential provider usage scenarios](https://learn.microsoft.com/en-us/windows/win32/api/credentialprovider/ne-credentialprovider-credential_provider_usage_scenario)

## 5. What does installation and signing cost?

- **Administrator installation.** Creating a service in Service Control Manager requires administrator privileges. Expect the install path to encounter UAC according to the account and policy. For a release, use a signed installer and signed native binaries, with an administrator-owned install location and separately reviewed update and removal. Microsoft requires Authenticode and a protected installation location for `uiAccess` applications. [Service access rights](https://learn.microsoft.com/en-us/windows/win32/services/service-security-and-access-rights) · [How UAC works](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/user-account-control/how-it-works) · [SendSAS requirements](https://learn.microsoft.com/en-us/windows/win32/api/sas/nf-sas-sendsas)
- **SmartScreen and application control.** A fresh download can show a reputation warning even with a valid signature. Smart App Control and managed application control policies can block execution. Signing establishes publisher identity while reputation and policy still govern the outcome. Validate the exact published installer through its real download path on a disposable Windows 11 machine. A locally built binary is a different case. Budget for a signing identity and CI signing on every release. [SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation) · [Code-signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) · [Application control](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/appcontrol)
- **Defender Antivirus.** Antivirus scans and behavior monitoring are separate from the installer publisher prompt and SmartScreen reputation. The alert or block outcome is unknown until measured for the actual build and target policy. Preserve protection settings in release qualification. [Microsoft Defender Antivirus overview](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-antivirus-windows)

## Paths ruled out or left open

The ruled-out paths follow from platform contracts or the parent spec. No runtime failures were measured.

| Path                                                           | Disposition                                                                                                                                                              |
| -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Ordinary desktop capture or input from the Bot Computer driver | Ruled out by desktop isolation and the parent spec's Human-only boundary.                                                                                                |
| Direct service interaction from Session 0                      | Ruled out by Windows service isolation.                                                                                                                                  |
| UI Automation value readback or input API success as proof     | Ruled out. The evidence required is Windows session state.                                                                                                               |
| Generic LocalSystem capture plus synthetic credential input    | DXGI has a documented capture privilege. Credential delivery and actual unlock remain unverified. Keep this out of the delivery plan pending a supported sign-in design. |
| OS-native local sign-in and explicit Computer resume           | Existing recovery path. The Human signs in through Windows and explicitly resumes the Bot when ready.                                                                    |
| A standalone Credential Provider using Windows authentication  | Documented extension point for a separate design review. Its deployment, recovery, device binding, and compatibility need their own qualification.                       |

## What #5143 can implement and verify first

1. Keep Windows unlock capability off by default. Expose unavailable, canceled, and completed outcomes to the Human without exposing an unlock operation to a Bot, model, Bot tool, or general Computer input route. Keep Windows authentication authoritative and preserve the built-in local sign-in path.
2. Bind authorization to the paired Human device, the native helper's pinned identity, the Windows account, the locked console session, and one fresh user action. Refuse a changed helper key and require explicit re-pairing. Cancel or refuse on unknown screen, account mismatch, session change, recovery UI, or multiple actionable password fields. Expire an attempt on cancel or disconnect. An expired attempt, a reconnect, and an automatic lock must never trigger a new attempt.
3. Design around native-endpoint encryption. The existing Connect channel terminates in the Host and its device grant is a general Host grant. It can inform routing and pairing design. The Windows secret channel must terminate in native code on Android and Windows, with its own helper identity and authorization. Keep passwords, PINs, protected input, and lock-screen imagery outside JS, Host TypeScript, Bot tools, logs, diagnostics, and relay storage. Audit only who attempted unlock, when, and the outcome. [Current Connect boundary](../decisions/connections.md#adr-0244) · [Parent security boundary](https://github.com/BotHarness/DeepSeekBot/issues/5134)
4. Separate Windows session state from request state. An account switch, console reassignment, or connection loss during an attempt invalidates the result. An unlock releases only the sign-in transaction. Require the existing durable Computer pause before any protected Human interaction. Bot access resumes only after the Human explicitly selects **Resume**. Keep exit and idle locking off by default, and require fresh biometrics for the next supported phone unlock. [Computer takeover and pause](../decisions/computer.md#adr-0245) · [Parent spec](https://github.com/BotHarness/DeepSeekBot/issues/5134)
5. Exercise identity pin changes, cancellation, wrong-account state, ambiguous or recovery UI, unavailable capability, stale events, and continued Bot pause against synthetic session events in an ordinary test environment. The test data should contain no real credential or lock-screen image. Scope the first sign-in design review to local-account password with the inbox password provider available as recovery. Treat Microsoft account and PIN as separate qualification decisions.

For any later Human-led validation of a supported sign-in design, use a disposable Windows 11 test machine or VM with dedicated test accounts and recovery access. Record the Windows build, account and provider type, and applicable policies as found. First use built-in Windows sign-in to verify the observer distinguishes a same-session unlock from cancellation and switching users. Then qualify the installed, signed build through the Android journey in #5143, observing saved-password success, manual entry, cancel, and wrong password as separate outcomes. Verify that the Bot stays paused across each outcome, and record redacted results without credential text or protected input. Qualify the Windows bare-metal console separately before claiming support on physical machines.
