# Design-token best practices for a dense desktop/Web app (2025–2026 survey)

Issue: [#4282](https://github.com/BotHarness/DeepSeekBot/issues/4282) · ADR: [0348 Tobs owns its design tokens](../adr/0348-tobs-owns-its-design-tokens.md) · Researched 2026-11-16.

**Question.** What do current design systems do about token tiers, scales, dark mode, density, focus, accent theming and component tokens? Where do the values in `design/tokens/tobs.tokens.json` sit against them? How should Tobs support three switchable style themes (A quiet, B native, C tonal) on top of light/dark and the accent presets?

**Short answer.**

- **DTCG format.** The DTCG format has had a stable 2025.10 release since 28 Oct 2025. Our file uses the older string syntax for colours and dimensions, and it keeps dark values in `$extensions`. The 2025.10 Resolver module is the standard way to express light/dark, style and accent as orthogonal modifiers, and IBM Carbon already ships one.
- **Scales.** Our spacing, radius, focus width, icon size and elevation scales are inside the industry range. Our default control (28px) and body text (13px) are on the dense edge, and only macOS and Geist's "space is a premium" styles match them.
- **Contrast outlier.** The real outlier is contrast: tertiary ink is gated at 3:1, below the 4.5:1 that WCAG and every surveyed system require for small text.
- **Three styles.** All three can be one shared colour/ink/spacing core plus about 25 style-scoped tokens: radius roles, row heights, list container model, selection fill, control shape and icon size. Most of the open decisions are listed in §11.

Method: every number below comes from the owning system's published token files, package source or official docs, read on 2026-11-16. Package versions are pinned in §0. "Unverified" means the primary source does not state it, or could not be read here.

## 1. W3C DTCG: status, tiers, modes, composites, `$extensions`

**Status.** The overview says 2025.10 is a "Final Community Group Report, 28 October 2025", published "as a Candidate Recommendation", and "considered **stable**. Further updates will be provided in superseding specifications." The modules are Format, Color and Resolver ([TR/2025.10](https://www.designtokens.org/TR/2025.10/)). The home page says "First stable version 2025.10 now available" ([designtokens.org](https://www.designtokens.org/)). It is a Community Group report, not a W3C Standard. A living draft continues ([drafts/format](https://www.designtokens.org/TR/drafts/format/), "Draft Community Group Report 08 September 2026"). No 2026 numbered release exists: `/TR/2026.10/` returns 404.

**Value syntax changed from the older drafts.** This matters for our file.

- Colour `$value` MUST be an object `{colorSpace, components, alpha?, hex?}`, and `hex` is only an optional 6-digit fallback ([Color §4.1](https://www.designtokens.org/TR/2025.10/color/)). Fourteen colour spaces are supported, including `srgb`, `oklch` and `display-p3`.
- Dimension `$value` MUST be `{value, unit}` with unit `px` or `rem` ([Format §8.2](https://www.designtokens.org/TR/2025.10/format/)).
- Duration `$value` MUST be `{value, unit}` with unit `ms` or `s` (§8.5).
- Shadow is a composite: an object, or an array of objects and references, with `color`, `offsetX`, `offsetY`, `blur`, `spread` and an optional `inset` (§9.6).
- Typography is a composite with `fontFamily`, `fontSize`, `fontWeight`, `letterSpacing` and `lineHeight`. `lineHeight` is a **number** that "SHOULD be interpreted as a multiplier of the fontSize" (§9.8).
- Other composites are border, stroke style, transition and gradient (§9).
- File extensions are `.tokens` or `.tokens.json`, and the media type is `application/design-tokens+json` (§4).

**`$extensions`.** Keys are vendor-specific, and reverse-DNS naming is recommended. Tools MUST preserve extension data they do not understand. Teams "SHOULD restrict their usage of extension data to optional meta-data that is **not crucial to understanding that token's value**" (Format §5.2.3).

**Tiers.** The Color module names three categories: **Base** (the lowest level), **Alias** (a reference to another token) and **Component** ("design decisions at the component level"; example `color.button.primary → {color.brand.primary}`) ([Color §7.1](https://www.designtokens.org/TR/2025.10/color/)). It describes descriptive and numerical naming for base scales. It does not mandate a tier count.

**Modes and themes: the Resolver module.** A `.resolver.json` document has `version: "2025.10"`, `sets` (always-included token sources), `modifiers` (each with a `contexts` map of context name to token sources, plus `default`), and a `resolutionOrder` array, where later entries override earlier ones ([Resolver §3–4](https://www.designtokens.org/TR/2025.10/resolver/)).

- Its worked example is a `theme` modifier with `light`, `dark` and `darkHighContrast` contexts.
- It defines _orthogonality_: modifiers that each own exclusive tokens, so their order does not matter. It recommends orthogonal modifiers "as much as possible".
- The number of resolutions is the product of all modifiers' context counts (§4.1.5.4).
- A modifier MUST NOT reference another modifier.

### 3.5 Icons, strokes, borders

## 8. Component-level tokens: when systems add them

- **Add them** when a component's values must vary by theme or size and are reused across platforms. Carbon puts button, tag and notification colours inside each theme context of its resolver. M3 generates `md.comp.*` for every component, which lets Expressive swap shapes per state. Primer adds `control-*`, `overlay-*`, `stack-*` and `button-*` for cross-component sizing families.
- **Stay semantic-only** when a strong primitive library owns the composition. Atlassian has no component tokens and enforces `prefer-primitives` and `no-html-*` through eslint. shadcn has only the `sidebar-*` region group. Radix keeps per-component variables internal.
- The DTCG Color module treats the component tier as optional ("improve the separation of concerns").

## 9. Swappable shape, density and style independent of colour mode

This is the scope addition: three style themes, A quiet, B native and C tonal.

**How systems separate these axes.**

- **Radix:** `appearance` (light/dark), `accentColor`, `grayColor`, `radius` (none/small/medium/large/full as multipliers 0/0.75/1/1.5/1.5, with `full` also turning on 9999px pills) and `scaling` (90–110%) are **independent props on one `<Theme>`**. Each is a data attribute (`[data-radius='large']`, `[data-scaling='95%']`) that only rewrites its own variables (`radius.css`, `scaling.css`). This is the cleanest precedent for "style ⟂ mode ⟂ accent".
- **DTCG Resolver:** one modifier per axis: `mode: {light, dark}`, `style: {quiet, native, tonal}`, `accent: {classic-blue, mist-purple, forest-green, warm-amber}`, giving 2 × 3 × 4 = 24 resolutions. Keeping them orthogonal (style sets never define colour values, mode sets never define shapes) makes order irrelevant ([Resolver §2.1](https://www.designtokens.org/TR/2025.10/resolver/)). Carbon's `themes.resolver.json` is a shipping example with one modifier.
- **Tokens Studio:** `$themes.json` groups (mode, style, accent) of token-set combinations. sd-transforms recommends one CSS file per permutation. With orthogonal sets, three scoped blocks (`[data-mode]`, `[data-style]`, accent variables) cascade correctly without 24 files.
- **M3 Expressive:** shape is per component _and per state_. Hover, press and selection morph corners: list item 4 → hovered 12 → pressed and selected 16; button full → pressed small 8 (`ListTokens`, `ButtonSmallTokens`).

## 10. Cross-surface consistency (one design language across every panel)

**What the systems do.**

- **Shared layout primitives over per-screen styling.**
  - Primer: React primitives (`ActionList`, `NavList`, `PageHeader`, `Stack`, `Overlay`), fed by control, stack and overlay token families, so lists in every product share item height and padding (`ActionList-*.css` reads `--control-medium-size`).

  - Atlassian: layout primitives (Box/Stack/Inline). Its eslint `prefer-primitives` and `use-heading` rules push code onto them.
- **Lint enforcement.**
  - `@primer/stylelint-config`: rules `primer/colors`, `primer/spacing`, `primer/typography`, `primer/borders`, `primer/box-shadow`, `primer/responsive-widths` (README).
  - `@atlaskit/eslint-plugin-design-system`: `ensure-design-token-usage` ("Enforces usage of design tokens rather than hard-coded values"), `no-unsafe-design-token-usage`, `no-deprecated-design-token-usage`, `prefer-primitives`, `no-html-button`, `no-html-text-input`, `no-html-select`, `no-html-textarea`, `no-margin`, `no-physical-properties` (README).

`ds/NavItem` and `ds/NavGroupHeading` (ADR-0348) are the first two: they become `ListRow(nav)` and `SectionHeader`. Adding a dimension-literal rule to `check-design-tokens.mjs`, like `primer/spacing` and `carbon/layout-use`, would stop panels from drifting out of the style system.

### 11.2 Open decisions for the owner

Each decision has options and a recommendation, grounded in the sections cited.

**D1. Token file format.**

- (a) Keep the current strings plus `$extensions` dark values.
- (b) Move to DTCG 2025.10 values (`{colorSpace, components, hex}`, `{value, unit}`), with dark values in a separate set file.
- (c) Option (b) plus a `tobs.resolver.json` with modifiers `mode`, `style` and `accent`.

_Recommend (c)._ 2025.10 is stable, Carbon ships exactly this, and three orthogonal axes are the Resolver's design case (§1, §9). The generator keeps emitting the same `--tobs-*` CSS.

**D2. UI body size.**

- (a) 13/20 everywhere.
- (b) 14/20 everywhere.
- (c) Style-scoped: 13/20 for A and B, 14/20 for C, plus a separate shared `type.message` token for chat transcript text.

_Recommend (c)._ 13 is the macOS default and Geist's dense choice. Every web system and M3 use 14 (§3.3). Long chat text is the "copy" case where Geist uses 14/20.

**D3. Tertiary ink contrast.**

- (a) Keep the 3:1 gate.
- (b) Raise tertiary ink to ≥4.5:1 for text and add a separate ≥3:1 `ink.quiet` for icons and decoration only.
- (c) Restrict tertiary to ≥24px or non-text.

_Recommend (b)._ WCAG 1.4.3, Atlassian, Primer and Apple all set 4.5:1 for small text (§4). The current light value fails on `well`.

**D4. Default control height.**

- (a) 28 for all styles.
- (b) 32 for all (Primer and Radix default).
- (c) Style-scoped: 28 for A and B, 40 for C.

_Recommend (c)._ It matches macOS (28pt) and Primer `small`, and M3 (40) for C. 24 remains the floor (WCAG 2.5.8).

**D5. Radius structure.**

- (a) Keep the size-named scale only.
- (b) Add semantic roles (`radius.control`, `field`, `container`, `overlay`, `list-group`, `list-item`, `nav-selected`), set per style over a shared primitive scale `0/4/6/10/12/14/16/20/28/full`.

_Recommend (b)._ Atlassian documents role usage. Radix and M3 swap roles without touching components (§3.1, §9).

**D6. Accent role derivation.**

- (a) Keep runtime `color-mix`.
- (b) Generate, per accent and per mode at build time, a fixed role set (`solid`, `solid-hover`, `on-solid`, `container`, `on-container`, `tint`, `ink`, `focus`), contrast-tested, and keep runtime derivation only for a free custom colour.
- (c) Adopt Radix-style 12-step scales per accent.

_Recommend (b)._ Radix and M3 derive the same role list ahead of time and guarantee contrast. Option (c) is more than four presets need.

**D7. Accent-fill selection in dark (style B).** White text on accent needs a darker solid in dark mode, but our dark `on-accent` is dark ink (`#0d1220`).

- (a) Add `accent.selection` per mode with white ink in both modes, as on macOS.
- (b) Use the existing dark accent with dark ink.

_Recommend (a), unverified against current macOS rendering._ The HIG describes white text on accent highlight (§6), and B is meant to map 1:1 to SwiftUI.

**D8. Focus ring.**

- (a) 2px outward with offset 2, as Radix and Geist do.
- (b) 2px inset with offset −2, as Primer and Carbon do.
- (c) Outward for controls and inset for list rows, with a new `edge.focus-offset` token, and a per-style width (3 for C to match M3).

_Recommend (c) with the width kept at 2px for all styles._ It meets WCAG 2.4.13's 2px perimeter and survives clipped scroll lists (§6).

**D9. Icon stroke.**

- (a) Keep 1.75 user units (≈1.17px at 16).
- (b) Define the token in rendered px (for example 1.5px) and apply an absolute stroke.
- (c) Use the Lucide default 2 (≈1.33px).

_Recommend (b)_, so the token means what it says. Pick the px by eye; no source sets a desktop standard (§3.5).

**D10. Selection cue.**

- (a) Fill only.
- (b) Fill plus ink and weight change (A), accent fill (B) or tonal fill with accent ink (C).
- (c) Add a leading indicator bar.

_Recommend (b)._ It keeps 1.4.11 safe without new chrome (§11.1).

**D11. Density as its own axis.**

- (a) None; the styles imply density.
- (b) A separate `density` modifier (compact/regular) across styles.
- (c) A Radix-like `scaling` percentage.

_Recommend (a) for now._ Each extra axis multiplies resolutions (Resolver §4.1.5.4). Primer and Carbon show density as per-component choices, not a global mode.

**D12. Component/style tokens scope.**

- (a) Semantic-only, like Atlassian.
- (b) Style tokens only for the §9.2 families (list, nav, control, segmented, chip, switch, overlay).
- (c) Full `comp.*`, like M3.

_Recommend (b)._ That is where the three styles differ. Everything else stays semantic.

**D13. Where styles apply.**

- (a) Every surface, including chat bubbles and the composer.
- (b) Navigation, lists, settings, menus and controls only, with the chat transcript shared.

_Recommend (b) as the starting point_, so switching style does not reflow reading content. The owner may want C's pill composer, which can be one token (`radius.composer`).

**D14. B on mobile.**

- (a) Style B on iOS uses native SwiftUI `List(.insetGrouped)` and reads only colour roles from `core`.
- (b) Mirror the B tokens in React Native.

_Recommend (a)._ ADR-0348 already lets mobile keep its own semantic layer and native controls.

**D15. Tertiary-gate test scope.** The contrast test today covers canvas, raised and well. Should it also cover `field`, `sheet`, `elevated`, and accent ink on `accent.tint` and `accent.container`, for all 2 × 3 × 4 resolutions? _Recommend yes_, as Primer's CI contrast check does per theme (§4).

### 11.3 Not verified here

- M3 density guidance, the M3 text-field and dialog shapes, and anything on m3.material.io. The site is client-rendered and was not readable here.
- Apple inset-grouped radius, separator inset, macOS push-button and sidebar row pixel heights, and System Settings row height.
- Linear token values. Only design-process posts are public.
- Atlassian control heights and its DTCG source format.
- Geist button heights are read from the vercel.com site CSS, not from a published token file.
