# ADR-0340: Uncertain connection writes stay Client execution state

Accepted for Environment E11 ([#4120](https://github.com/BotHarness/DeepSeekBot/issues/4120)). Stopping the route or revoking the grant carrying a management request can lose its acknowledgement after the owning Host has acted. The Client records an execution guard before one transmission and requires the same pinned Host’s canonical readback before resolving an uncertain result; it never converts ordinary management writes into a replay queue. Device Pairing, private-route and account capabilities remain the configuration and authorization authorities.

The guard lives in execution-only keys under the existing Client HostStorage owner, separately from the SavedHost configuration array. Otherwise another already-open tab’s unrelated whole-array write could erase the unknown-result guard. Its identity binds the Host ID and public key, device grant, operation generation and exact operation/route ID. One shared Web Lock covers prepare/persist, one write and acknowledgement, and fresh readback with generation CAS. Lock waiting and execution obey the request deadline, capped at 30 seconds. Missing Web Locks refuse dangerous writes with guidance to a supported secure page or the owning environment’s local CLI; insecure remote HTTP pages are not claimed equivalent.

A verified alternate route is tested through the existing HostClient, selected by an explicit manual-preference change, observed as the actual connected route and checked with the authenticated Host owner before writing. Without that handover the Human explicitly confirms disconnection. Ordinary manual route policy does not silently fail over. A private route stop names its owning route ID, preserving sibling routes and foreign mappings; account sign-out, relationship disconnect and individual device revocation remain distinct operations.

Private-route confirmation binds an opaque configuration revision returned by the owning Host. The same revision travels from the displayed plan through UI or CLI confirmation, dispatch, acknowledgement and uncertain-result readback. The Host compares it inside its existing lifecycle serialization before any stop write or runtime close; replacement, deletion/re-addition or Host restart makes an old confirmation stale. Configuration and revision publish together after successful persistence. Runtime health and port updates retain the configuration identity. A Quick public endpoint change renews it atomically and requires a new confirmation; no revision is derived from a connector token. A same-ID replacement cannot be stopped by an older confirmation, and its off state cannot settle an older unknown result. Legacy private-stop records without a revision remain unknown. Existing explicit unconditional local-owner controls retain their semantics.

The existing Owner-only RemoteHosts provider also gates execution-history access and local forgetting. Member and Admin pages do not hydrate Owner credentials or execution records. Its `owner-required` refusal remains an authorization refusal, not a prompt to restore storage. An exact-grant readback refusal retains the unresolved record and never falls back to a Native Owner request.

Account enrollment and manual configuration changes share the existing short credential transaction: fresh-read the raw SavedHost array, compare the exact credential generation, then persist only configuration. Execution projections are derived again after that transaction and never serialized into the credential array. When both are needed, the execution Web Lock precedes this short configuration transaction; configuration writers never acquire the execution lock. Enrollment retains its separate per-Host intent lock before the same configuration transaction.

Execution refreshes the persisted grant under that short transaction after acquiring its execution lock, and validates it again at dispatch after any planning or handover awaits. The final synchronous callback checks the request deadline and actual route before recording a new guard. It then atomically records the guard and starts the existing SDK request, without publishing intermediate callbacks between the check and request initiation. The network Promise is wrapped rather than awaited by the credential transaction; other configuration writers can proceed while the original network request remains in flight. Replaced/missing/unreadable persisted ownership refuses dispatch even if a storage event has not updated the provider cache. A same-grant route change that now disconnects this Client requires the original explicit disconnect consent or a still-valid verified handover.

Public route lists and plans expose normalized origins only. Management resolves those origins back to the exact saved SDK route before probing, saving a preference and comparing the actual connection; URL credentials, paths and query values are not returned as public plan alternatives. Acknowledgement follows the existing operation-specific Host HTTP contract: exact-device revocation, LAN off, named private route off, or account signed out. A successful HTTP status with HTML, unknown JSON or an incomplete acknowledgement remains uncertain and does not release the guard.

New guards are embedded in a `{ version: 3, entries: [...] }` envelope at the existing execution-index key, so one atomic HostStorage `setItem` commits or clears the complete execution fact instead of independently writing an index and a second record key. A failed initial write leaves the previous document intact and dispatch does not start; a failed acknowledgement clear retains the same readable generation for canonical readback without replay. Version2 inline envelopes and legacy arrays of index-to-record references remain readable and are not silently discarded or interpreted as fresh state when their record is missing or corrupt. Every index key, including a completed tombstone, must match the owner-generated operation-key prefix and canonical three-string Host/pin/device identity; duplicate keys or mismatched identities refuse storage access before cleanup. Confirmed clearing of a legacy reference first commits an inline completed tombstone, then attempts obsolete-key cleanup. Failure of that cleanup leaves a readable completed fact; later operations prune only confirmed tombstones after cleanup succeeds, never unresolved legacy facts. Once no entries remain, the same atomic write restores the legacy empty array `[]`.

This execution format is forward fail-closed. The older array-only parser and version2 reader both reject the entire version3 envelope, including when they attempt to manage another Host. An older whole-index writer therefore cannot strip another Host's unknown payload or newly added configuration revision. The current reader accepts version2 and legacy references, but older Clients cannot read back new facts. Code rollback is therefore conditional: resolve outstanding operations and tombstone cleanup with the current version until the index returns to `[]`, or preserve the guard and use a version that understands it. Do not delete the execution index to make an older Client writable, and do not claim that configuration rollback reverses a completed device revocation.

Changing a device grant does not inherit or replay its predecessor’s write. An older unresolved operation blocks further management mutations on that Host until explicit same-pin readback confirms completion; changing grants cannot bypass it. Recovery route selection and probing remain available. A changed pin refuses that readback. An indexed but missing execution record is a storage refusal, never fresh state or a candidate for silent pruning; saved Hosts and already loaded Feed/conversation data remain available. Restoring the record permits explicit readback. At most 32 unresolved execution facts are retained; further mutations refuse rather than pruning unresolved history. An unchanged or unavailable owner value remains unknown because it cannot prove an in-flight operation will never finish. Only the owning route’s documented pre-write coded refusals release a guard without completion readback.
