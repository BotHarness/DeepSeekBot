# Cross-Host Bot DMs use online communication without outgoing queues

In the accepted design target of [#3250](https://github.com/BotHarness/DeepSeekBot/issues/3250), active PersonaBots in the same verified Tailscale tailnet or Tob Connect account automatically discover and contact one another through ordinary Bot-to-Bot DMs. Ordinary LAN discovery requires explicit admission to the collaboration scope. Contact queries include the Bot's owning Host/device facts, available capabilities and public description; the originating Bot chooses the colleague. The application-defined device communication bridge extends existing contact and message capabilities into the receiving Host's Channel and Bot Inbox authorities, preserving ADR-0065's conversation model and each Bot's private Memory and execution permissions.

Communication requires an online reachable device. Definite unavailability is a failed delivery; losing acknowledgement after transmission may produce an unknown outcome. Neither result creates an executable persistent outgoing intent, automatic retry or reconnect/startup replay, including for replies. The Bot decides whether to preserve a task, explicitly contact the colleague later or ask the Human. Accepted DM history and receiver Inbox persistence remain canonical and recoverable; they are not an outgoing transport queue. Receipt deduplication protects the same message identity without introducing a resend subsystem.

Temporary loss of connectivity affects communication, not existing local authority. Actual withdrawal from the collaboration scope prevents new communication and not-yet-started work from that relationship. Already-started work may finish under local permissions but cannot send results to the departed counterpart. Existing processing states and causal hop guards continue across Hosts. Routes do not create new Bot identities or grant general Human device-management access.

## Why

Bots need to choose useful colleagues by device and responsibility, while follow-up behavior remains controlled by their users. A durable outgoing queue would turn an unavailable send into a future external action without a fresh Bot decision. Provider paths with durable Outbox recovery must not lend their retry semantics to this bridge. A central dispatcher, copied private Session relay or additional Memory authority would obscure existing ownership boundaries.

## First Tailscale slice

The application-defined device owner reuses the existing Profile Host identity and binds a narrow Bot directory/message listener to the local Tailscale address. Current daemon membership and Tailscale whois establish the socket peer's collaboration scope. The directory advertises the existing device Noise public key; its contents alone never authorize a message. The existing Noise XK implementation proves both Host keys and encrypts one message and its acknowledgement. Its prologue binds the ordered sender and receiver Host IDs. Incomplete handshakes are bounded, expire and close on disposal; they contain no executable pending message.

First contact trusts an eligible tailnet device's advertised identity, then requires proof of possession before pinning its public key in the existing remote Channel participant. This is trust on first use within the verified tailnet, not independent proof of the first advertised Host name. The Channel owner atomically enforces one key per remote Host across its Channels, including when another local Bot first contacts that Host. On a first inbound relationship, the normal Channel creation atomically stores the authenticated key and membership before admitting the message; a pre-existing Channel is not required. Existing relationships retire withdrawn work before rebinding, and the Host-wide key check still runs before acceptance. Subsequent key changes are refused. The listener exposes no operator API or Device management credential; discovery routes remain volatile and no additional identity or message store is introduced.

The Channel owner stores a remote participant as Host plus Bot identity, with a distinct remote author kind. Only the real local Bot belongs to local Inbox admission. Both sides keep accepted history through their existing Source Event and Channel placement transaction. The sender writes accepted outgoing history only after remote acknowledgement; uncertain outcomes are never scheduled for resend. Public contact data in the Client is a current contact-query projection, not persisted private Bot state.

## Membership lifecycle

The existing remote Channel participant also retains the authenticated local and remote stable tailnet node IDs. This provenance belongs beside the pinned Host key: route caches and public contact descriptions cannot authorize recovery after a Host restart. Replacing that binding first retires old relationship Admissions that have not started, then updates the Host binding and admits the new message. Transitions for one Host are serialized in memory; they contain no outgoing message intent.

The device bridge owns a bounded, read-only subscription to native Tailscale member notifications. Numeric removal IDs are mapped to stable IDs from the initial status and subsequent peer changes. An observed removal is processed even if the next snapshot already shows the peer rejoined. A backend requiring login withdraws the local relationship; a stopped/unreachable daemon or an offline peer alone does not. Current status queries and socket whois remain the admission authority, and peers explicitly absent from the current network map cannot be authorized from transport caches. The watcher closes with the bridge, reports coded lifecycle failures without raw notifications, and is restarted by the existing device lifecycle. Its version-sensitive notification contract requires qualification against the installed Tailscale CLI.

BotRuntime cancels only existing unobserved, side-effect-free pending/retryable Bot DM Admissions. It retains the Source Event, Channel history and Human inspection path; cancellation survives database reopen. S1 Channels without authenticated membership provenance are not evidence of temporary route loss. Recovery retires their unobserved, side-effect-free pending Admissions with an explicit provenance-unavailable reason, retaining messages and history. A new authenticated exchange can establish membership for future work; it does not revive retired work. Started work remains under local execution authority. A new send or reply must pass current membership and recipient checks after authentication, so completing local work does not imply permission to reply. Failed cancellation remains a withdrawal until the existing owner can complete it.

Contact queries refresh public facts. Human conversation views and the existing online `channels` CLI expose `available`, `unavailable`, `withdrawn` or `bot-unavailable`, without exposing remote execution state. Archive/delete checks run again on send; a same-name replacement has its own Bot identity and Channel. Explicitly contacting a third colleague preserves the causal root and parent, while the existing 32-hop wake limit and independent network eligibility remain in force.

## Delivery status

This ADR records the confirmed target. Implementation and runtime qualification of the first route belong to [#3251](https://github.com/BotHarness/DeepSeekBot/issues/3251), and membership/colleague lifecycle qualification to [#3252](https://github.com/BotHarness/DeepSeekBot/issues/3252). Connect, route continuity and explicit LAN admission remain dependent slices. Test evidence for one route does not prove those other routes or replace live Host acceptance.
