# ADR-0254: Live Activities project one admitted DM request

Status: Accepted for the source slice; provider deployment and native qualification pending

Date: 2026-10-26

## Context

A Human should be able to explicitly follow a request from an iPhone Lock Screen. The phone cannot depend on foreground JavaScript while suspended. Ordinary Expo Push notification delivery does not implement ActivityKit delivery. Arbitrary Human Computers must not receive the app's Apple signing key.

DSH Session history and BotHarness's existing Source Event, Inbox Admission and explicit Inbox resolution remain the execution authorities. A handled turn, an idle Bot, a failed attempt and a disconnected phone do not establish that the Human request is complete.

## Decision

The first application-defined display projection covers one Human DM request initiated by this phone. The screen retains the ID returned by its existing send operation; it offers tracking only after that exact message is committed in the same Computer/Channel. Host preparation then verifies canonical admission and provider capability before ActivityKit starts. The phone never creates activities automatically. Starting another requires explicitly stopping or switching the current display. Stop does not cancel, resolve or resend the request.

Extend the existing `channelSendStatus` receipt with a minimal progress projection. Only explicit `resolution=done` is completed; `ignored` ends with unknown. `retryable` and `needs-repair` are unknown and nonterminal. Other accepted/open requests remain working until explicit resolution or staleness. There is currently no reliable terminal **failure** fact in this projection: a failure card or attempt failure must not invent one. This remains a limitation of #2815.

The Device Gateway derives Device identity from its admitted credential; body-supplied identity grants nothing. Its exact activity paths use the existing pinned-key encrypted carrier. The existing Connect account owner supplies the owning Host credential; Connect verifies that the authenticated account owns that exact Host. Host-authoritative Device Pairing is the enrollment authority. L1 adds no independent mobile-to-Connect enrollment protocol.

Connect owns a bounded delivery registration, not a Task ledger: an opaque server handle binds Host, Device and native activity ID to a per-activity APNs token. Updates identify that handle and the bound Device, never an arbitrary token/topic. Rotation cannot change the request or revive a retired activity. The Host stores only opaque handles and original request identity, not APNs tokens or another copy of execution history. Device revocation, explicit stop, account removal and Host unlink retire delivery; unreachable cleanup has an eight-hour registration expiry.

Only the managed Connect Worker owns APNs signing material. Its environment explicitly selects the fixed supported app bundle and Apple production/sandbox endpoint. Missing or malformed configuration refuses capability before a phone starts. The source slice supports configured Connect accounts only, even if a phone currently reaches that Computer over encrypted LAN or Tailscale. A LAN-only Computer refuses tracking. Ordinary Expo Push remains unchanged.

The APNs content contains status, last authoritative update time, locale and the owned Connect Host's bounded public display name. No hostname fallback, conversation body, Bot output, tool arguments, approval question, filesystem path or credential is sent. Activity deep links contain a local opaque reference; the phone resolves the persisted original Computer/Channel/request and rechecks source and DM identity before navigation. It does not trust a destination supplied by a link.

Delivery revisions and pending content persist before I/O. Natural completion remains pending until provider acknowledgement, with the same revision retried after a five-second exponential backoff capped at two minutes and the registration expiry. Connect uses a conditional delivery lease, exact-content idempotency and monotonic APNs timestamps; a failed terminal send cannot admit a nonterminal update. A lost acknowledgement can be repeated without another send. Stop/revocation immediately fence status delivery and ask Connect to scrub the token; a transient stop failure is reported to the caller and retained as cleanup-only work under the same bounded backoff/expiry. New tracking waits for cleanup acknowledgement, preventing a stranded server registration. Natural completion scrubs the token only after acknowledgement. Sweeps coalesce and release the Host serial owner between registrations, so slow delivery does not accumulate a queue of sweeps. Content refreshes only on projection changes or a two-minute heartbeat; the OS marks it stale after five minutes without an update. APNs retries are bounded to three attempts with the same timestamp. Invalid tokens are erased. There are at most 32 unexpired registrations per Host and one active registration per Device. Terminal activities request dismissal after two minutes; disconnected nonterminal activities are also bounded by ActivityKit's own lifetime. Owner disposal aborts in-flight Host provider calls and fences queued work and late acknowledgements before further database writes. Bounded developer records include initiator, duration and outcome/refusal code, never tokens, handles or content. Provider acceptance is not delivery evidence.

The phone persists only original IDs and display-cleanup intent. It restores an existing native activity and token observer, never recreates a dismissed activity. Transient token-registration failures retain the card and retry registration on the next foreground sync; they do not invent a task failure. Sign out/removal passes the old saved connection to presentation cleanup before credentials are lost. The request target selects its paired Host for preparation, registration and connection observation even when another Computer remains globally selected. Browsing an already paired conversation through HostScope is not a source selection. The phone records the existing selected Host ID as the display baseline and fences in-flight work with HostSession's source-change revision projection. That read-only, process-local generation advances only when an existing valid selection intent could change the current source, or when adoption changes the selected pairing identity. It records a boundary change without choosing or persisting a source; the generic navigation revision remains unchanged. Pairing replacement advances the generation even without a navigation intent. Re-selecting the same Computer and removing an unrelated pairing do not end the display, while an A-to-C-to-A intent still invalidates pending work. An explicit new source selection, target pairing removal/replacement or target-client refusal stops local presentation and retires the original registration; it never retargets the card. Restart compares the saved selection baseline, with older records using the original target Host as their baseline. Restore and token rebind revalidate the source after registration returns. Concurrent sync requests coalesce into one running pass plus a requested-pass flag, so source changes during I/O are drained without accumulating a queue or waiting for another foreground event. Failed remote cleanup retains a bounded retry intent and expires remotely.

## Consequences and qualification

`device-activity capability|prepare|register|stop --device-file …` uses the same live Device routes. Pairing credentials stay in a private file; ActivityKit tokens enter through stdin and never appear in output. `send-status` exposes the existing receipt and the new progress fields.

The app adds Expo SDK 58's `expo-widgets` and its CNG plugin. A new native binary is mandatory; existing TestFlight/development clients cannot validate this source. Widget layouts use native SwiftUI text and the OS stale environment. No foreground timer pretends to provide background delivery.

This decision authorizes source implementation only. No provider credentials were read, accounts configured, relay deployed, native build started or release published. A queued iPhone run must still prove background/locked delivery, cold start and same-name Bot navigation, source/sign-out/revocation cleanup, system dismissal, disabled permission, light/dark and Dynamic Type/VoiceOver, latency and battery impact. Those gates are UNTESTED. No FPS, energy, real APNs acceptance or native delivery claim follows from source tests.
