# ADR-0336: Hosts have members — identity, credentials, roles and audience containment

Status: Accepted design — Human confirmed the complete Team mode design (Q1–Q35) on 2026-11-13. Implementation, migration and runtime acceptance remain separate gates.

## Context and trade-off

A Host serves one Human today. The data model is already partly keyed by Human ID (Group membership in `channel_human_members`, read positions, Activity snoozes and dismissals), but the only value is the literal `local-human`, hard-coded in Activity queries and the Channel store. PersonaBots have no owner, approvals go to "the Human", Workspace Grants record only `actor_kind = 'human'`, Paired Device credentials bind a device to a Host but not to a person, and Tob reads every Bot and Channel.

Small teams want one Host (a VPS or an office computer) to serve several people, each with an independent identity, private Bots and shared public Channels, so that Bots become colleagues who accumulate team context. This is orthogonal to the Environment work (ADR-0334): Environment is one Human across several Hosts; Team mode is one Host serving several Humans.

We considered (a) a separate "multi-user mode" with its own tables and a second code path, (b) embedding Better Auth, and (c) requiring Connect (WorkOS) accounts. (a) doubles every feature. (b) introduces a second session store beside the existing device-grant authority, which ADR-0326 deliberately avoids. (c) makes a team Host depend on the cloud service and email. We choose a Host-owned member model that is always present, with a policy switch.

## Decision

- **Always multi-member.** Every Host has exactly one **Host Owner**; the existing `local-human` becomes that Owner without rewriting its Human ID. **Team mode** is a policy switch that permits additional **Host Members** and requires every non-local Client to sign in. A single-Human Host is the one-member case, not a separate code path.
- **The Host is the identity authority.** A `humans` record holds identity only (Human ID, display name, status, roles). Login methods live separately as **Member Credentials**; the first provider is a local username/password (argon2id). A future OIDC provider maps an external subject to the same Human ID, letting an organisation point many Hosts at one IdP; Hosts never synchronise member directories with each other. No Better Auth session layer and no Connect dependency.
- **Credentials bind a person.** Each Paired Device grant is (device, Host, Human ID). A Client holds at most one active identity per Host; signing out revokes that grant only. Existing grants bind to the Owner when Team mode is enabled. The Host-local Desktop shell and loopback access act as the Owner without a password by default (OS access already reaches the database), with an option to require it. The local `deepseekbot` CLI acts as the Owner; `--as <member>` evaluates commands with that member's permissions for verification and never bypasses checks.
- **Transport.** Password sign-in from anywhere other than loopback requires HTTPS or the encrypted device gateway. Plain HTTP refuses password sign-in unless the Owner explicitly enables a persistently warned "trusted network" exception. Invitations carry the Host address, Host identity fingerprint and username; the one-time initial password is delivered out of band and must be changed at first sign-in. A signed-in member may pair another of their own devices without retyping a password.
- **Gateway default-deny.** The API Gateway remains the sole Host/Client interceptor. For non-Owner members it denies every DSH-native method by default and allows only BotHarness methods that resolve and enforce the calling Human. Members see the Tobs Client only.
- **Roles.** The Owner is unique, transferable and not a role. Other members hold one or more **Host Roles** from a fixed **Host Permission** catalog (union semantics, Discord-style); built-ins are Admin and Member, and the Owner may define more. First delivery has no per-object permission overwrites beyond Channel membership roles, Channel visibility and Bot visibility. Viewing others' private content is a separate permission held only by the Owner unless explicitly granted; every such access writes an audit record and members are told in Settings that it is possible.
- **M3 transfer provenance guard (#4164).** An Owner-transfer target must have completed the forced change of a credential issued by the current Owner. Member-manager issuance and unknown historical provenance are ineligible until the current Owner resets the credential and the intended Human changes that reset secret. Credential JSON records the Owner issuer; self-service changes preserve it. This establishes an API-enforced recovery boundary against a member manager retaining an initial secret; it trusts the Owner's direct out-of-band delivery. See the [M3 transfer rule](../architecture/team-mode.md#m3-owner-transfer-credential-rule) for the invariant and refusal.
- **Role Policy is advisory.** Host-level natural-language rules ("may access finance information: Deny") reuse the existing Behavior permission item semantics (Allow/Deny, Deny wins, declared exclusions) and one evaluator, with Host Members as an additional subject kind beside paired external people. A Bot answering a Human receives that Human's identity, roles and effective items. The UI states that policy guides Bots and is not access control. An "ask" value is deferred.
- **Audience containment** is the hard rule: content may flow only to an object whose audience is a subset of the content's audience: every Human who can read the destination must already be able to read the content. Comparing audience sizes is not enough.
  - Bots carry `owner_human_id` and a visibility of `private`, `roles:[…]` or `shared`. A shared Bot has one Memory; making it shared states that it remembers every member's conversations with it. A role-restricted Bot may join only a Channel visible solely to those roles, or a private Channel whose every member holds them; adding a member who lacks the role is refused with an explanation.
  - Channels have visibility `public` (browse, preview, explicit join), `roles:[…]` or `private` (invite only), plus Channel owner/admin settings for adding members, posting, @all, adding Bots and editing details. DMs are `dm` Channels: Human–Bot, Bot–Bot and the new Human–Human. Group Channels already hold many Humans and Bots.
  - Workspace access follows OS-like roots: every member gets a personal root; admins create shared roots granted to roles or members. A personal root may be granted only to its owner's private Bots; a shared root only to Bots whose audience it covers. A Grant that is inside, or is an ancestor of, another member's root, any Bot's Memory repository or the Host data directory is refused for everyone, so a Grant such as `/` cannot reach them.
  - Bot–Bot DMs are readable only by the participating Bots' owners and audited private-content viewers.
- **Approvals.** An approval card stays where the work happened. Every Channel member sees that a request exists; only authorised approvers see its content and decide. Approvers are the Bot's owner and holders of approval permission for that Bot, including the Human whose request caused the work when they hold it. When no approver is present, the request also reaches the Bot owner's Activity. In Team mode, opaque tools (Shell and similar DSH asks, ADR-0205) of a member's Bot can be approved only by holders of the opaque-tool permission (default Owner and Admin), with an explicit "this reaches the whole Host" warning; the dangerous Assignment preset is Owner-only; member Bots never run with a DSH mode that suppresses those asks.
- **Per-person attention.** Activity, read/clear/snooze state and push delivery are per Human ID. Bot Inbox stays per Bot; every Source Event carries the speaking Human's ID. Each member has their own private Tob, acting with that member's authority and never above it.
- **Management, compute and lifecycle.** Shared Bots are managed by their owner and holders of the all-Bots management permission. Binding a Bot to an external IM App requires Bot ownership plus the external-IM permission (default Admin); external people stay in the Chat pairing system and never become members. Model providers and keys stay Host configuration; roles may restrict usable models; usage is attributed to Human ID and Bot; no quotas in first delivery. Disabling Team mode suspends non-Owner members (grants revoked, data retained, private Bots not woken); re-enabling restores accounts with fresh sign-in. Offboarding is deactivate → transfer owned shared Bots, Channel ownership and shared-root grants → separately confirmed permanent deletion through Content Purge, with authorship retained as a deleted member.
- **Host Relationships stay Owner-scoped.** Reciprocal relationships and same-account enrollment (ADR-0334, ADR-0327) authorise the Owner's Clients. Members do not inherit them and reach other Hosts by signing in there.

## Security boundary

First delivery is **permission isolation among colleagues, not OS isolation against a hostile member**. ADR-0067's guard confines path-addressed tools but is not a same-user process sandbox; an approved opaque command can reach the whole Host, including the database. That is why opaque approval and the dangerous preset are restricted above. The intended long-term direction is a per-execution OS sandbox (Linux Landlock/bubblewrap first, then macOS Seatbelt, then Windows AppContainer) whose filesystem allowlist equals the Grant plus Memory, delivered through DSH's Execution World Provider seam as its own specification. Per-member OS accounts and per-member containers were considered and rejected for root requirements, cross-platform cost and loss of local-computer capabilities.

## Amends

- ADR-0067: Workspace Grants are additionally bounded by member and shared roots and audience containment.
- ADR-0334: relationships and derived enrollment are Owner-scoped in Team mode.
- Glossary: Human ID, Paired Device, Tob and Activity become per-member; new Team mode terms.

## Verification and delivery

Deliver as tracer bullets under a dedicated spec and hub, parallel to the Environment hub. M0 threads explicit Human context through Host methods with no behavior change. M1 is the first end-to-end slice: enable Team mode, set the Owner password, create a member, sign that member in from a LAN browser over HTTPS, show only the Tobs Client, join a public Channel and exchange messages with the Owner, with matching CLI. Seek Human feedback before broadening. Every slice proves refusals as well as successes: a member cannot read another member's private Bot, Channel, DM, Workspace root or approval content through the Client, the Gateway, the CLI with `--as`, or a Bot tool call.
