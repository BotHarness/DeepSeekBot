# Local Computer video separates media, control and durable pause

The Human needs to watch a Bot from a phone and occasionally click, scroll or type on the Local Computer. JPEG polling couples observation to a pause lease and cannot guarantee smooth motion. The new viewer uses WebRTC video without an image fallback, while the Computer owner independently manages observation, exclusive Human control and a durable pause of Bot activity. These are accepted design decisions; the screenshot implementation has not yet been migrated.

## Scope and transport

The first runnable slice is a single Windows display viewed on a physical Android phone, with existing click, scroll and text input. It serves our Android and Web viewers rather than targeting VDO.Ninja/OBS interoperability. Multiple admitted viewers may watch, but only one can control the Computer. Audio, clipboard synchronization, file transfer, monitor switching, PiP, background viewing and automatic desktop unlock/lock are outside this slice. Other platforms retain their existing implementation until separately migrated.

WebRTC first attempts a direct connection. Users may configure their own TURN; this release supplies no project-funded public TURN and promises no universal connectivity. The media adapter must not silently acquire a supplier's public TURN credentials or inherit a relay default. Hosted Connect may carry authenticated signaling and commands; it is not a video relay. Each receiver's media transfer still consumes bandwidth, including when the sender is user-owned.

**The new viewer has no JPEG/PNG fallback, automatic or manual, on any network.** Missing capture support, failed ICE negotiation or interrupted video produces an explicit unavailable/reconnecting state with retry and relevant TURN setup guidance. It never starts frame polling or offers single-image viewing as a substitute. This removes a second presentation/transport lifecycle and prevents failed video from silently becoming continuous image traffic through Connect. Existing Bot screenshots and diagnostic capture are separate capabilities, not fallback viewers.

## Ownership in DSH

- **Plugin/Fiber (Cordis-native):** the existing Computer Plugin owns its live Provider, native capture helper, encoder, peer connections and bounded diagnostics. Fiber disposal stops them; the helper is a supervised Subprocess, not another Host or Agent Session. A native media dependency must not be able to terminate the DSH Host during teardown.
- **Service Definition / Provider / Consumer (DSH capability seam):** Computer viewing and control are application-defined capabilities owned by the Computer module. Route, CLI and Client adapters are Consumers of the same owner. Keep admission, single-controller arbitration, pause transitions, stale-input rejection and resource cleanup behind its Interface; callers must not coordinate these invariants themselves. A media adapter can be replaced without reimplementing these rules.
- **Persistence (application-defined):** a Computer-owned durable record is the sole authority for the Bot pause. Use the existing product persistence seam; concrete storage and API names must be verified against pinned DSH source before implementation. Do not persist ephemeral controller grants as restartable authority or turn a viewer into a DSH SessionEvent, Memory entry or second permission store.
- **API Gateway / Typert:** reuse the existing authenticated Host/Device gateway and the single `/api` interceptor. Signaling and control requests bind the admitted caller to the Computer and current runtime/control generation. Media admission and revocation remain Host-enforced after a peer connection is established. Closing only a signaling socket is insufficient to revoke a direct video stream.
- **Host Feed:** publishes current viewer/control/pause status only. Video stays on the media path. Web and Android share the platform-neutral Host client contracts and supply platform playback/input adapters; native media bindings do not belong in that shared layer.

Keep input on authenticated Host commands for the first slice, reusing the existing driver operations. WebRTC does not require migrating input to a DataChannel. The Host rejects requests that lack the current controller authority even if a Client presents enabled controls. No new public signaling service, pairing identity or generic transport registry is needed.

The shared Connect carrier owns pairing-to-key trust and fresh authenticated channel binding to the intended Host, device and connection generation. Video consumes that contract, including tamper/replay rejection and revocation, rather than choosing another encryption protocol. First enrollment must state its trust assumptions separately from later key pinning. Keep the existing Host/Device gateway and Computer Provider; do not transplant a full-Harness Typert Gateway method switch for this capability.

Each concrete viewer connection and media attempt owns its pending requests, subscriptions, buffers and callbacks. A replacement connection invalidates only its predecessor; stale completion or close callbacks cannot dispose the replacement or another viewer, even when clients use identical local request/stream identifiers. Install authorized handlers and cleanup ownership before advertising ready. Bound queued messages/bytes, in-flight work and cleanup time; overload refuses or closes the affected connection. Revocation evidence must show media delivery actually stops and the corresponding peers/tracks are released, not merely that signaling closed. Shared capture may continue for other admitted viewers.

## Three independent lifetimes

**Observation** admits an authorized viewer without pausing Bots or granting input. Each viewer's media attempts can reconnect without creating or renewing control authority. A new attempt invalidates stale signaling and cannot inherit access after a device is revoked or the Computer runtime changes.

**Control** belongs to at most one admitted viewer of the Computer. Explicit takeover first establishes the durable pause, blocks Bot actions/screenshots and drains in-flight operations before enabling Human input. Failure to persist the pause or drain operations must not grant control. Each grant has a fresh generation; the Host checks it at execution, not merely when a request is queued. An authorized second device may explicitly confirm a forced takeover: invalidate the old grant and resolve its in-flight actions before admitting new input. Old queued/late inputs are refused, not replayed.

**Pause** applies to all PersonaBots using that Computer and blocks model-facing screenshots as well as actions. It survives controller release, lease expiry, helper failure and Host restart. Restart restores the pause before admitting Bot operations but restores no old controller grant. An authorized Human explicitly resumes Bots; resuming invalidates any remaining control grant and drains Human input before reopening Bot operations. Persisted state and execution fences must remain consistent if a write or process fails.

The Human can release control while leaving Bots paused, or explicitly end control and resume Bots. A receiver's video failure alone does not hand control to someone else. Confirmed stalled video disables click/scroll/type; control lifecycle actions remain available. A static desktop is not a stalled pipeline: verify capture/media liveness and receiver presentation, with refresh/keyframe requests within the video path where needed. A live signaling heartbeat alone does not establish a fresh picture.

Control connection loss immediately stops accepting input from that connection. The Host reserves its authority for at most 30 seconds to allow authenticated reconnection; expiry releases control and leaves Bots paused. Another device's observation does not extend that window. Known foreground-to-background or phone-lock transitions stop media and explicitly release control, leaving Bots paused; if that notification is lost, the same expiry rule applies. Foreground return restores observation, with an explicit new takeover required.

Recovery has one owner, a finite retry budget and at most one attempt in flight. After each delay, recheck the selected Host/Computer, authorization, runtime/attempt generation and foreground state. Target changes, explicit disconnect, backgrounding, revocation and non-retryable refusals cancel old recovery; exhaustion exposes manual retry. Preserve the selected remote target while disconnected and refuse operations instead of silently routing them locally. Reconnection never replays a mutation whose acknowledgement was lost, even if it may already have executed, and does not extend the control reservation deadline.

These semantics deliberately replace ADR-0210's automatic Bot resume after 30 seconds without frame polls. All entry points into the same Computer, including legacy routes, must obey the new owner when migrated: a bare `active: true` request or an old image poll cannot bypass exclusive control or change the pause. This is an authority migration as well as a video change.

## Mobile interaction and delivery evidence

Use the existing viewer family's mobile interaction vocabulary: a touchpad with visible cursor, optional direct pointing, local zoom/pan, scrolling and phone-side text composition. The richer Web reference is the Local Browser viewer; the Web Computer wrapper itself mostly embeds Selkies. Native Computer already reuses the Browser stage and mouse pad. Reuse coordinate/input semantics where appropriate, not iframe or image-rendering assumptions. Viewing, zooming or moving a local cursor must not silently acquire control; only an explicitly granted controller can send remote actions. Map displayed video coordinates through fit/zoom/letterboxing to the captured display's coordinates.

Current native input auto-acquires takeover and can reacquire/retry after a `not-paused` response; the new path must remove both behaviors. Native incremental text forwarding does not establish correct Android IME commit semantics. Use the Web Browser's composition-aware behavior as a reference and verify Chinese candidate selection, replacement, backspace and password input on the physical phone. Never replay uncertain text or clicks after reconnect, and never record their content in diagnostics.

The first tracer bullet includes the owning Host behavior, installed helper, authenticated signaling, real Android presentation, explicit takeover/input, visible pause/resume and matching CLI commands. A standalone encoder demonstration or a successful signaling probe is preparatory evidence, not completion. Deliver focused automated coverage of authority and lifecycle regressions and run the real slice before broadening platforms or features.

Initial LAN acceptance targets are at least **15 presented frames/second during continuous motion** and **input-to-visible-response p95 at most 500 ms**, with readable static text. State test hardware, display resolution, codec, bitrate, scene and measurement method; do not count repeated static frames or substitute network RTT for end-to-end input latency. Then measure real cross-network direct and user-configured TURN paths: first-frame time, presented frame rate, bitrate, selected ICE path and input feedback latency. No arbitrary-public-network SLA is implied.

Derive the reported media path from the actual selected ICE candidate pair, not configuration preference. Missing statistics remain unknown/unavailable. Where supported, expose RTT, send/receive byte counts and available bitrate separately from receiver presentation and input feedback measurements. Diagnostics identify the connection attempt, phase, failure source and retryability within bounded storage; published evidence omits raw SDP, credentials, input content and unredacted addresses. Test slow consumers and queue limits as well as successful negotiation.

Verify concurrent observation, forced takeover, device revocation, late input rejection, media/control loss, phone backgrounding and Host restart, including the absence of unintended Bot resume and screenshot fallback. Report capture/encoding/receiver limits honestly. CLI status and probes expose the same owner and coded refusals but do not prove that a phone rendered a frame. No performance or device behavior has been verified by this design-only change.

## T1 implementation choice — 2026-10-22

The first slice uses a separately supervised Electron 44.9.3 Windows x64 process for primary-display capture and Chromium VP8 WebRTC, with a native Android Expo module using `io.github.webrtc-sdk:android:144.7559.15`. The helper retains sandboxing, context isolation and a local-only renderer; no native media teardown occurs inside the DSH Host. Gathered SDP crosses the existing authenticated gateway while the video track goes directly between peers. The helper has no configured ICE servers. Source progress, encoded progress and receiver rendering are measured separately; repeated output frames cannot establish source health.

The [official Electron release](https://github.com/electron/electron/releases/tag/v44.9.3) archive is 158,508,870 bytes with SHA-256 `41a1ffa0541cb0f2c9b9fe920dd2cef1793ad0ea2ada1a9582958880f4d1b23c`. The existing explicit Local Computer install/start flow acquires and verifies it. The [Android release](https://github.com/webrtc-sdk/android/releases/tag/v144.7559.15) maps to WebRTC revision `30d5e63ae91da483e06577b5c35ee91cc5e5c3db`; its AAR SHA-256 is `fc7c8d027eb33860ccbb7847988f7f942d44a92d1f575348bba6c0250cde4071`. This choice avoids loading a native RTC addon into the Host and avoids a second pairing/backend. It adds a substantial Windows runtime download and an Android development-client rebuild. License files remain with both dependencies. Source provenance is verified; installed Windows compatibility, static-capture cadence, Android rendering, extracted footprint and performance remain qualification gates, not established results.

The Computer-owned pause record is atomically replaced under the existing application data directory. It stores only a version and pause boolean. Viewer/attempt/controller generations stay process-local. Device gateway admission supplies the device identity directly to the owner; proxy headers and request bodies cannot assert it. Local Host commands use its authenticated owner identity. After integrating the encrypted carrier and LAN listener, T1 dispatches the exact video command path directly from the server-owned LAN channel to this owner with its Noise-admitted device ID. Default Connect channels refuse it before owner or loopback effects; normalized aliases cannot bypass that restriction. The outer Connect stamp is not assumed to survive decrypted loopback forwarding. This preserves channel-only Connect without expanding T1 into remote media.

Older versions do not read the new durable pause record. After takeover, downgrade therefore requires coordinated recovery: keep Computer stopped, confirm owned media cleanup and preserve pause. Only an explicit Human decision permits the supported resume/drain operation before downgrade; otherwise use a forward fix that honors pause. No automatic downgrade or unpause behavior is added.

## Alternatives and evidence

Cindy usefully separates media attempts from control and credential lifetimes; its Electron capture environment is not the Node DSH Host. The initial design considered VDO.Ninja's SDK as a candidate media dependency, not the owner of DSH identity, control or capture. Its CLI/MCP workflows add unrelated process/browser authority, and its SDK requires concrete signaling and capture integration. Neither open source licensing nor a publicly available relay establishes an unlimited free media budget. The initial design selected no dependency; the T1 implementation choice above records the subsequent selection and its unverified runtime gates.

The accepted [design interview](../research/2026-10-22-local-computer-viewer-design.md) links the pinned [current-viewer audit](../research/2026-10-22-remote-viewer-webrtc.md), [Cindy implementation audit](../research/2026-10-22-cindy-remote-desktop.md), [media cost research](../research/2026-10-22-cindy-media-cost.md) and [VDO.Ninja evaluation](../research/2026-10-22-vdo-ninja-viewer.md). Historical issue [#1833](https://github.com/BotHarness/DeepSeekBot/issues/1833) proposed a local helper with image fallback and no TURN; it is closed following reconciliation with #1836. That issue status is not proof of this design's video path or acceptance results, and this ADR does not reopen it or claim its old proposal was implemented.

The Human also accepted the [ds-harness-remote comparison](../research/2026-10-22-ds-harness-remote-comparison.md) on 2026-10-22. Its encrypted DataChannel RPC, per-connection ownership and diagnostics informed the refinements above and existing slice acceptance; it supplies neither our desktop capture nor Computer control semantics. Its bundled self-hosted Server is Relay-only and does not establish a free video relay budget. This follow-up selects no library, adds no slice and changes neither the no-image-fallback decision nor the direct/self-configured-TURN cost boundary.
