## Shared design standard

All new or changed screens follow the cross-platform [UI design standard](../../docs/agents/ui-design.md) ([中文](../../docs/agents/ui-design.zh.md)) and its review gate. Layout, icons and interaction communicate the task; descriptive prose supplies only necessary context. The native component and accessibility rules below implement that standard on each platform.

## Overlay contract

[Mobile overlay standard](./OVERLAYS.md) ([中文](./OVERLAYS.zh.md)) defines presentation choice, handle/header/body anatomy, immediate versus transactional changes, dismissal, platform differences and acceptance gates. It is the target contract for new or changed overlays; its audit records current gaps, including the provisional iOS Settings fix in #2112.

## Native first

On both platforms the system's own design and components are the standard: Apple's Human Interface Guidelines on iOS (`ios-hig` skill), Material 3 on Android (`android-material` skill). Where the platform has a component for the job, use it (native navigation, `@expo/ui` SwiftUI views on iOS, `@expo/ui` Jetpack Compose views on Android) and keep its default look and behaviour; do not draw a React Native look-alike or restyle it into a house style. A custom surface is allowed only where no native component fits, and its reason is written in this file first.

Tokens come in three layers ([ADR-0266](../../docs/adr/0266-mobile-design-tokens-have-a-shared-layer-and-a-layer-per-platform.md)):

- **Shared:** brand accent, status colours, spacing and content-only colours (`tokens.ts`, `palette.generated.ts`). These match the Web.
- **Android:** chrome colours come from `useMaterialRoles()` (Material 3 roles seeded by the accent), with type from `materialType`.
- **iOS:** chrome colours come from `systemColors` (semantic system colours), with type from `systemType` (Dynamic Type styles), and the accent is the tint.

Platform files never hard-code a colour.

Android chat-to-profile dragging uses a real retained profile in a native Material side-sheet container (#3146; [ADR-0271](../../docs/adr/0271-android-profile-drag-keeps-the-real-scene.md)). The native-stack header sits outside that moving scene, so this entry has a narrow custom-content exception: the existing accessible identity Chip and Back control move with the chat and composer inside the native content slot. iOS keeps its native-stack header. Do not add independent JS frame updates or replace the scene on release. Profile visibility controls refresh and subscriptions separately from the chat's route focus.

Native controls draw platform icons: SF Symbols on iOS, Material symbols or vector drawables on Android. A React Native view inside a native control is only for avatars and images. Never nest React Native inside Compose inside React Native.

On Android the shared `Button` (`src/ui/primitives/button.android.tsx`) is the Material 3 Compose common button in the Host's default look: `primary` is a filled button, `secondary` and `tonal` are filled tonal buttons, `variant="text"` is a text button, and `danger` is a filled button (or text button) in the `error` / `onError` roles. Its leading `symbol` is an outlined Material symbol exported as a vector drawable under `assets/button/`, 18dp like `ButtonDefaults.IconSize`; it takes no React Native icon. Busy replaces the symbol with the native circular progress indicator at the same size, inside the button, and disables it. The button keeps the 48dp touch target, fills the caller's width and grows with the label at any font scale. Creation screens import the same button through `creation-button`; there is no second Android button (#3005).

On Android every caller of the `Sheet` shell (`src/ui/chat/sheet.tsx`) opens the Compose Material 3 `ModalBottomSheet` (`sheet-frame.android.tsx`), fully expanded, with the system drag handle in the Host's default look. Drag, scrim tap, Back and predictive back all call the caller's close. The content stays React Native inside `RNHostView` with `matchContents={{ vertical: true }}`, so the sheet takes its height from the content at any font scale; the content is capped at the window less the safe areas, two touch heights for the handle and the keyboard, and scrolls inside that. The sheet window pads its content above the navigation bar and the keyboard, so Android ignores `avoidKeyboard`. Every scroll view in a shell sheet sets `nestedScrollEnabled` so scrolling hands off to dragging the sheet at the top; `test/sheet-android.test.tsx` checks the callers (#3018).

On iOS every caller of the `Sheet` shell opens a SwiftUI sheet (`sheet-frame.ios.tsx`, the `@expo/ui` `BottomSheet`) with the system grabber, resizing, swipe-down dismissal and the system background, which is Liquid Glass on iOS 26. Swipe-down and the header's close button both call the caller's close; a caller that refuses to close while busy gets its sheet presented again. The content stays React Native inside `RNHostView` with `matchContents={{ vertical: true }}` and reports its measured height: content that fits in half the screen opens at the medium detent, and taller content (for example the same sheet at the largest Dynamic Type size), an `avoidKeyboard` sheet or any sheet with the keyboard up opens at large (`sheet-detent.ts`). The content is capped at the large detent's room less the keyboard, so a field and its action stay above the keyboard and long content scrolls inside, handing off to the sheet drag at the top. The frame stays mounted until the system finishes dismissing, then calls the optional `onDismissed`; work that presents another screen (the statistics notice's Open Settings) waits for it with `dismissQueue`. `test/sheet-ios.test.tsx` checks the shell (#3019).

On Android counts and action cards are Material 3 components too (#3014):

- `CountBadge` is the Compose `Badge` with the count, capped at 99+. **Needs you** uses the shared `warning` with `fg` ink (`base` in dark), **Unread** uses `primary` / `onPrimary`, and **Muted** uses `surfaceContainerHighest` / `onSurfaceVariant`. The badge is hidden from TalkBack: the row, section header or drawer row that owns it says the count in its own label. The Activity navigation item keeps its icon and marks pending items with a `warning` dot badge in a `BadgedBox` (no number, as Activity shows Needs you as a yellow dot); the count stays in the item's description for TalkBack.
- `ActionCard` is the Compose filled `Card` in the theme's default shape, colours and tonal elevation, inside one `Host`; the focused card adds an `edge.focus` border in the accent. Everything inside is Compose: the header with the `warningSoft` status pill, the title, `CardPreview` and Details on a `surfaceContainerLow` well, `DetailRow`, `CardNote`, `CardField` (the filled text field), question options as radio or checkbox rows that toggle as a whole, the approval diff, the loading indicator and the shared `Button`. Primitives that already open their own `Host` (`Button`, `LoadingIndicator`) draw straight into the card's tree through `ComposeTreeContext` instead of nesting a `Host`. Sheets a card opens (the draft editor, the folder picker) render beside the card, never inside it. Card text is not selectable on Android; Details and the chat keep the full values.

The custom surfaces that stay custom, because no native component does the job:

- message bubbles
- streaming text reveal
- the Computer video canvas and its remote keyboard
- the Tob Mode entrance from the top: no native stack animation enters from the top edge, so the `dm-top` alias of the chat route is presented as a transparent modal with no system animation and slides itself; the screen inside is the unchanged chat screen (`app/dm/[slug]`) in a nested stack

The migration of the remaining look-alikes is tracked in [#3002](https://github.com/BotHarness/DeepSeekBot/issues/3002).

Older rules below that prescribe a custom surface where a native component exists describe the current implementation, not the target. Change them to the native component when the screen is next touched, and update the rule in the same change.

Back closes the topmost surface before it leaves the screen: an in-screen surface that is not its own route, such as the composer's attach tray, holds the screen with Expo Router's `usePreventRemove` and closes itself; the full client steps back through its web history first, while its floating exit still leaves at once. Do not add `BackHandler` listeners for new surfaces; the two existing ones (the Host drawer and header search) register through `holdBack` (`src/ui/shell/back-owner.ts`). React Native 0.88's `ReactActivity` registers an always-enabled `OnBackPressedCallback` on targetSdk 36, which hides the system's back-to-home preview. The local `predictive-back` module turns that callback off whenever nothing in the app can go back (no stack or tab history, and no `holdBack` owner), so at the root Android plays its own predictive back-to-home animation. Screens inside the app still do not follow the gesture's progress: that waits for react-native-screens' predictive back support. Remove the module once React Native ships `BackHandler.setInterceptEnabled` (react-native#59292).

## Motion

Motion follows each platform (ADR-0264). Pick a role from `spring` in `src/ui/design/motion.ts`; the iOS and Android values differ, the role does not.

| Role              | Use for                                                                               | iOS                                     | Android                            |
| ----------------- | ------------------------------------------------------------------------------------- | --------------------------------------- | ---------------------------------- |
| `spatial.fast`    | small feedback: a bubble, badge or menu appearing, a press released                   | SwiftUI `.snappy` (0.35 s, bounce 0.15) | M3 Expressive spatial fast         |
| `spatial.default` | a surface moving or resizing: the composer, a list closing a gap, the profile opening | `.smooth` (0.5 s)                       | spatial default                    |
| `spatial.slow`    | large surfaces travelling far                                                         | `.smooth` (0.7 s)                       | spatial slow                       |
| `effects.*`       | opacity and colour; never overshoots                                                  | `.smooth` (0.2 / 0.3 / 0.5 s)           | effects fast / default / slow      |
| `release`         | a dragged surface let go: drawer, swipe row, image or browser snap-back               | spatial default, critically damped      | spatial default, critically damped |

Time-driven animations (stream reveal, click ripple, long-press lift, fling-away) keep fixed durations with `decelerateCurve`. Screen pushes, sheets and menus use the system's own transitions.

## Application dialogs

- Application-owned confirmations and choice menus use `showAppDialog` (or `confirmDestructive` / `showActionMenu`) and the root `AppDialogHost`. Do not call React Native `Alert.alert` directly from a screen or feature. Per Native first, iOS shows system alerts (menus follow [iOS menus and native controls](#ios-menus-and-native-controls)), and Android shows the Material 3 `AlertDialog` from `@expo/ui/jetpack-compose`, themed by `seedColor` = accent. Operating-system permission prompts, photo pickers and the share sheet remain system-owned.
- A confirmation puts Cancel in the dialog's dismiss slot and the action in its confirm slot as text buttons; a destructive action's label uses `danger`. A menu (`showActionMenu`) is never a dialog, including when it has only one command. On Android it opens as an anchored Expressive dropdown at the point the finger touched (a long press, or a tap on the control that opened it), dismissed by Back or a tap outside. The root view records the last touch (`touch-anchor`); when there is no touch from the last 1.5 s, as with TalkBack activation or a menu opened after a wait, it falls back to the native modal bottom sheet with the same Expressive groups, dismissed by Back, scrim or swipe. A menu from a ⋯ button uses an anchored native dropdown (`ActionMenuButton`) containing the same groups. Destructive commands form the last group and use `danger`. A confirmation always states the consequence in its message, not only a title. Destructive menu choices open a second confirmation describing the consequence. Back and a tap outside dismiss without choosing. The system dialog handles width, scrolling at large text sizes, focus and TalkBack.
- Android command menus follow the [M3 Expressive vertical menu](https://m3.material.io/components/menus/specs), rather than the baseline menu: shared native Compose `MaterialMenuGroup` rows, 16dp outer corners, 12dp outer item corners, 4dp inner item corners, 2dp group padding/gaps, 20dp leading icons, 12dp icon-label spacing and native label-large text. Every command has an icon and a wrapping label; targets remain at least 48dp. Standard colors use the seeded native `surfaceContainerLow`/`onSurface` roles. Overflow, long-press, message, attachment and creation menus share this treatment. The pinned Expo wrapper exposes the baseline dropdown, so its transparent popup supplies anchoring/dismissal while native Compose groups supply Expressive content. Creation and attachment retain their existing anchored native popup positions.
- While an asynchronous action is pending, disable repeat submission and dismissal; close after success. On failure, keep the prompt and retry available. A menu opening a confirmation must not dismiss the newer prompt when its old callback finishes. Dialog requests are transient UI state, never a second persistence or authorization owner.
- Native checks include cancel/button/Back/backdrop paths, nested confirmation, light/dark and default/intermediate/maximum text. Verify the original pairing/group remains unchanged after cancellation, keyboard dismissal from focused search, and the actual rendering above an open drawer or profile. Record iOS and TalkBack qualification separately.

## iOS menus and native controls

Android inline peer choices use Material 3 standard button groups (native `ToggleButton`s with controlled single selection). Topic filters use native borderless `FilterChip`s: inset fill when unselected and chosen fill when selected. iOS keeps its segmented picker.

iOS choice controls are SwiftUI views behind the shared primitives (#3009):

- **Chips** (`Chip`: feedback tags, Routine schedules, Marketplace topics) are a SwiftUI `Toggle` with `.toggleStyle(.button)`, tinted with the accent. The selected chip carries the selected trait, and a count is part of its label.
- **Single and multiple choices** in a list (`CheckmarkRow`: Marketplace topics, the Activity options sheet, the Bot picker through `ParticipantChoice`) are whole-row plain SwiftUI buttons with a trailing `checkmark` SF Symbol, as in Settings. A chosen row carries the selected trait. iOS has no radio buttons or checkboxes, so rows never draw one.
- **The chat background sliders** (`PercentageSlider`) are the SwiftUI `Slider`, 0 to 100 in steps of 1. VoiceOver adjusts it natively and reads its value as a percentage.

This applies [Native first](#native-first) to iOS menus, following the Apple HIG (the `ios-hig` skill maps each component to our stack). Build them with `@expo/ui` SwiftUI views or native navigation, not with React Native views drawn to look like them. On Android the same jobs use Material 3 components: a dropdown menu for ⋯ actions, an exposed dropdown menu or radio dialog for a single choice, and a Material dialog for confirmations.

- **Action menus are native pull-down menus.** A ⋯ button opens a SwiftUI `Menu` anchored to it; a long press on a row opens a native context menu with the same actions. Items are commands with title-case labels, most-used first, related items grouped, at most one submenu level. Destructive items carry the destructive role and still open a confirmation describing the consequence.
- **Choices of one value are native pop-up menus.** A short, fixed set of mutually exclusive options shows the current value on the control, followed by the `chevron.up.chevron.down` symbol as in Calendar's Repeat row, and opens a menu-style picker with a checkmark on the selection. The options are text only: an icon goes on a menu item only when it tells that item apart, and then every item in the group has one (HIG Menus). A row that pushes to another page keeps the `>` chevron. Two to five peer modes that should stay visible use a segmented control (`Segmented`), with a one-word label per segment; a label that needs more words means the choice belongs in a menu or a list instead. Options that need explanation, search or a long list use a sheet.
- **Alerts are for confirmations and errors only.** A system alert asks one question with a Cancel and at most one or two actions; it never lists a menu of unrelated commands.
- **Exceptions stay as recorded.** App-owned tab presentation (ADR-0235) is a deliberate custom surface. Any new custom surface where the system has a control needs the reason written here first. The chat bubble menu is a native bottom sheet (see Chat), not a custom surface.
- Native menus inherit Liquid Glass, Dynamic Type, VoiceOver and Reduce Transparency from the system; do not restyle them. One colour rule applies (Human decision, 2026-10-28): an item's icon and label always share one colour, the text colour `fg` (black in light, white in dark) for ordinary items and `danger` red for destructive ones such as Unpair or Delete. Never the accent. `ActionMenuButton` and `ContextMenuArea` pin this with `tint(fg)` on the menu and a per-item `foregroundStyle`, so a menu inside an accent-tinted settings form does not turn its items blue; the Android dropdown draws ordinary icons in `fg` too. Every action in a context menu is also reachable from a visible control or an accessibility action.

Build a ⋯ menu with `ActionMenuButton` (`src/ui/primitives/action-menu-button`): a SwiftUI pull-down `Menu` with SF Symbols on iOS and a Material 3 `DropdownMenu` on Android, both anchored to the button. The Host drawer and the group member ⋯ menus use it. A long press on a row uses `ContextMenuArea` (`src/ui/primitives/context-menu`): on iOS a SwiftUI context menu anchored to the row (Host drawer rows, swipe rows in Activity and Routines), on Android the `showActionMenu` dropdown anchored at the finger. On iOS an action sheet only confirms a destructive choice; it never lists commands.

## iOS settings forms (#3011)

On iOS a settings screen is a SwiftUI `Form` (inset grouped list), so grouping, separators, row heights and Dynamic Type come from the system, as in the Settings app. Android keeps its segmented list.

- A screen wraps its sections in `SettingsForm` (`src/ui/primitives/settings-form`) instead of a `ScrollView`. On iOS that is an Expo UI `Host` holding a `Form`, tinted with the accent; elsewhere it is the existing scroll view. Inside it, `SettingsSection` becomes a form `Section` with its header and footer text, and `SettingsRow` becomes a native row. Screens keep calling the same primitives; nothing outside `SettingsForm` changes.
- A row is a `Label` with the row's `RowIcon` as an SF Symbol, the title and the detail under it. Its trailing slot picks the native control: a `Toggle` becomes a SwiftUI switch whose label is the row, a `CheckIcon` becomes a `checkmark` with the selected trait, `LoadingIndicator` becomes a `ProgressView`, and a muted text value becomes `LabeledContent`. A row that pushes another page keeps the system `chevron.right` and navigates through the caller's `onPress` (Expo Router). A `danger` row is a destructive button. `PreferenceRow` becomes a menu-style `Picker` with the `chevron.up.chevron.down` value.
- Each row is one VoiceOver element: the title is its label, the detail and any value are its value, and a chosen row carries the selected trait.
- Rows in one section look alike. A tappable row is a form button tinted with the primary ink, so its title, symbol and detail match the `Picker` rows instead of taking the accent. Every row in a section has an icon, or none does. A row that pushes another page shows its current value, if any, as a trailing value before the chevron, not as a second line; a detail line is for state the person must notice, such as a save error. A short fixed choice is one `PreferenceRow`, never a list of checkmark rows on the Settings root.
- React Native content inside a form (the Usage card, notices, a save-error retry) goes in `SettingsFormItem`, which hosts it as one row with no inset or row background. A leading or trailing view the form cannot map (an app-icon image, a row button) is hosted inside the row. Do not put a React Native `SettingsSection` or `SettingsRow` inside a hosted item; it renders as React Native there.
- Settings shown inside another scroll view (the Bot and group profile Settings tabs, sheets) keep the React Native inset-grouped rows until their screen moves to `SettingsForm`. Move a screen when it is next touched: replace its scroll view with `SettingsForm` and wrap any React Native blocks in `SettingsFormItem`.

## Activity query controls

- Activity has two header entries: **Filter and sort** and **Search Activity**. On iOS they share one Liquid Glass capsule, as related toolbar actions do in the HIG, and Filter and sort is a pull-down menu: Sort and Show are inline checkmark groups, **Unread Messages Only** is a checkmark toggle, and Bots and Conversations are one-level submenus. On Android, sorting is part of the same options sheet as category, unread-only, Bot and conversation filters.
- Filter and Search are the same `HeaderAction` buttons as the Chats header: Liquid Glass with SF Symbols (`line.3.horizontal.decrease`, `magnifyingglass`) on iOS 26 and later, the opaque `raised` circles on earlier iOS, and Material 3 standard icon buttons on Android. A button whose filter or query applies shows its glyph in `accent` and is marked selected for accessibility. Active search replaces the title, Filter and Search buttons with the same header search field as Chats, in the measured header row, so accessibility text can grow without clipping. Android uses the native Compose Material 3 docked search described below.
- Android uses the modal bottom-sheet surface, leading Material 3 radio buttons (Compose `RadioButton` through the `RadioMark` primitive) and system Back dismissal. Unread-only uses the `Toggle` primitive, so each platform gets its native switch. Long option lists virtualize and scroll; footer actions remain reachable.
- Options apply immediately and remain selected after swipe dismissal or Android Back; there are no Cancel/Done actions. Reset all immediately restores default ordering and the Needs you tab, with all Bots/conversations and unread-only off. Search is independent of this reset. The search field keeps the header's outer gutters; iOS search keeps its built-in clear control. Tapping blank list space or ending editing returns the header to its title and buttons and preserves the query for reopening, with the Search button tinted while a query applies, so Filter and sort stay reachable during a search. The close button (iOS) or back arrow and system Back (Android) clears the query. The focused Activity screen owns status-bar contrast for its current appearance.

## Chats source navigation (#2194)

The conversation header keeps its trailing area empty on iOS and Android: no file, overflow, lock-screen or text action. Tap the identity Chip to open the Bot profile, whose Files tab holds the DM's files. Bot-to-Bot Channels open the same full-screen page with only Files, without group management. iOS request tracking lives in the Bot Profile and retains explicit confirmation and its request scope. Back preserves the existing chat route, draft and reading position. Connection progress remains after the Chip name. The new detail actions reuse the native SwiftUI/Compose button adapter already used by creation; file browsing and permissions keep their existing owners (#2857).

Chats uses the same canvas and left-aligned title treatment as Activity. The title/chevron opens the workspace drawer; Settings remains on the right. One conversation list follows the existing device-local conversation filter, with no environment tabs or horizontal pager. The drawer's **All** row keeps the current management Host and includes online paired Hosts' conversations plus available cloud workspaces. Host choices queue their existing Host Session switches: each waits for the prior save/adopt to settle before checking the current Host, then selects that Host's filter only if no newer All or Host selection superseded it. The final Host owner, persisted Host and selected Host view therefore agree, including a return to the original Host while another save is pending. A failed switch does not block the next choice; All changes the filter immediately without cancelling an already requested Host switch. Every paired Host has an independent foreground connection; drawer selection changes presentation. The header shows All with the Chats icon in the accent colour, or the selected Host's local name and Host glyph in its contrast-adjusted colour. Android's root accent follows the current Host's local colour for the active scheme only when that Host's filter is selected. All, cloud views, a different Host filter and a Host without a colour keep the default accent; iOS retains its system accent; its Chats title returns to the workspace panel at the root of the Chats stack ([iOS workspace panel](#ios-workspace-panel-3017)). The title button announces the full selected view name, including existing cloud disambiguation. Its icons scale with the title text role; the drawer All icon scales with its body label. The All row clips Android foreground ripple over both selected and unselected backgrounds. Cloud entries still obey the cloud feature flag.

Chats connects all paired Computers concurrently (#2782). All includes loaded online Computers and existing authorized Organizations, with one collapsible Pinned section and recent-message ordering within pinned and ordinary rows. Computer sections apply only in their own scope. Selecting a scope filters the directory without disconnecting other Computers. Offline Computers are omitted from All; their status remains in the drawer. An open chat retains its source, history and draft, with offline sending disabled and no automatic resend. Activity and its preference-aware count aggregate the same online Hosts. Records, filters and pagination retain their source; approvals, answers, clear/snooze/undo and notification destinations use that source. Search and creation remain in their existing list-header placement until #2195/#2196. Activity inherits scope and keeps action/replies/unread paging; unsupported Cloud scope has an explicit notice and no borrowed Computer badge. All discloses that Cloud activity is not yet included. Source-owned history, credentials, drafts, permissions and send paths stay unchanged.

The older Host-band and environment-strip descriptions below record prior presentation behavior. The Chats Header and drawer selection above supersede those entry layouts; Host customization (name, icon, colour) remains available in the drawer.

## Quiet mobile waiting (#2802)

Transient connection progress belongs after the name label inside the Channel or selected environment identity chip, never over the avatar. Use the iOS system activity indicator and Android native Material 3 circular progress indicator. It is distinct from Bot activity and does not insert a connecting/reconnecting row above content. Actual unreachable/refused states retain the existing retry or pairing action. An open Channel retains permitted loaded history and its editable draft during reconnect; unavailable sending stays understandable. This presentation consumes the existing source owner and does not start a second connection lifecycle.

Cold Chats uses the existing native-view list skeleton; a warm same-source refresh keeps its rows. Initial failure has recovery instead of an empty-list message. An actual empty result and a search with no matches remain distinct from loading. Loaded Cloud conversations remain actionable while the directory refreshes: opening supplies immediate scoped feedback, checks current access, and ignores obsolete completions after leaving or changing identity. Existing navigation remains the route authority.

Blank Bot creation keeps destination, name and persona in a short form. Bio/tags and inherited-model explanation remain under optional Details. Submission replaces editable fields with progress and retains its existing fixed target and operation receipt. Completion opens the ordinary DM without an extra created-only model banner. Model settings remain reachable from the Bot profile; model availability does not gate creation or trigger an automatic probe. iOS creation actions use SwiftUI and Android uses Compose. Git, Marketplace and Zip reuse this journey with their source confirmation and recovery constraints. Source inspection labels the primary action Checking source; submitted import progress retains its title and suppresses premature retry. Source pinning, archive identity and receipt recovery remain owned by the existing creation controller.

Native qualification follows [the QoL feature journey](../../.agents/skills/verify-deepseekbot/features/phone-qol.md). Source tests do not establish first-visible-frame placement, safe-area geometry or native-control accessibility.

## Android creation forms (#2673)

**Create blank Bot**, **Import from Git**, and Remote Host **New Channel** open full pages with the standard native navigation header and Back action. Forms use the Settings/profile grouped surfaces, native editable inputs, Compose action buttons and native participant checkboxes. Keyboard-aware scrolling owns fields and the primary action in the same scroll container; the channel participant list remains virtualized. Drafts, Host selection and uncertain submission recovery stay in the existing creation controllers. Closing a page does not create or discard a submitted operation. Marketplace confirmation and Zip retain their existing flow, with the same full-page presentation.

All requires explicit choice among every paired Remote Host inside the form; a Host-scoped entry inherits and displays that Host. Selecting a target does not switch the browsing environment. Group Channel creation presents Host first, then name and a virtualized list of eligible Bots with native checkbox rows. Changing to a different Host clears selected PersonaBot IDs and candidates immediately, retains the channel name, and ignores old reads. Switching back never restores old members. No Host means no Bot selection; loading, empty, failure and retry have separate states.

The selected Host owns validation, membership and creation. Blank/Git use their existing recoverable operation; channels reuse the existing Channel creation operation key. The phone saves the submitted Host, pairing identity, input and key before mutation. A submitted request cannot be retargeted; retry replays its original key. Cancel/Back before submission creates nothing. Leaving accepted work does not cancel it or trigger navigation from another screen. A retained channel operation exposes Continue channel creation, and confirmed completion offers Open channel. Native keyboard, light/dark, default/intermediate/maximum system text and TalkBack checks remain separate acceptance gates.

A fresh Channel request explicitly rejected before acceptance returns to an editable draft. The same refusal on a retained/recovered request, or after a transport failure on another route, cannot prove non-acceptance: keep its submitted input and key. A renamed/archived/deleted candidate is rechecked by the Host during creation; the form offers a fresh candidate read for correction after a known refusal.

## iOS Computer viewer

The iOS Computer viewer uses the chat's native push navigation and transparent navigation bar, with swipe-to-leave disabled. A leading system Back button exits the viewer; it releases the viewer's input grant without resuming paused Bots. The title is the active paired computer's local display name, never the Bot that opened it. The single-line navigation title keeps semantic Dynamic Type and its full accessible name; status glyphs have separate accessible labels. A green dot requires both a connected Host and live native frame presentation, amber means waiting, and a warning glyph means disconnected. This is picture availability, not a latency or connection-stability score. Hand, CPU and pause symbols distinguish Human control, Bots allowed to operate and paused Bots; unavailable ownership stays unknown.

The video canvas and letterboxing are pure black in both app appearances, with a local dark media-control palette. UIKit owns the transparent navigation controls. ## Step bar and Environment selection

Accepted 2026-10-26 (#2922). Adding Environments and creating a Bot share one pinned bottom bar and one selection idiom.

- **Step bar.** A `StepBar` primitive pins the flow's action above the bottom safe area: an optional round Back button and a capsule primary button of the same height (iOS 52pt, Android 56dp, never below the touch target). The capsule names the action and, in a multi-step flow, the step (“Next · 2/3”); its accessible label speaks the step in words. Busy shows the platform's native indicator inside the capsule and disables it. iOS 26 uses Liquid Glass (`glass` / `glassProminent`) and falls back to bordered styles on earlier iOS or with Reduce Transparency; Android uses Material 3 Expressive `FilledTonalIconButton` + `Button` with the Expressive loading indicator.
- **Environment.** These flows call a paired Host an Environment (环境), per `CONTEXT.md`.
- **Selection list.** Choosing Environments uses whole-row selection with one native checkmark: a trailing `checkmark` on iOS, the selected settings-row fill plus a check on Android. No row embeds a checkbox control. Already-added Environments say “Added” and are not selectable; offline ones are disabled.
- **Adding from a Tobs Connect account.** The bar's capsule reads “Add N Environments” and is disabled until something is selected. Pairing keeps the list visible: the row being paired shows the native indicator and “Adding…”, then its result. The verification page replaces the list only while a fingerprint needs the Human's comparison or approval.

- **Step-by-step creation.** Creating or importing a Bot is a sequence of real stack pages, one question each, opened by one sentence saying what it asks: blank ① Environment ② Name ③ Persona, bio and tags; Git ① Environment ② Git link ③ Name ④ Bio and tags; Zip ① Environment ② Zip file ③ Name ④ Bio and tags; Marketplace ① Environment ② Name ③ Confirm. One pure function of the source owns the order. The capsule reads “Next · k/n” and “Create”/“Import” on the last page; the round Back button is hidden on the first page. iOS swipe-back, Android back and the round button go back one page; the header ✕ (no back chevron) leaves the whole flow and keeps the draft. Name is required; persona, bio and tags are optional.
- **Android creation chrome and fields (#2958).** These full-page flows share the Chats page canvas (`theme.color.base`) across the top app bar, body and pinned footer; they do not use a raised sheet body under a darker header. The native Compose `TopAppBar` has a standard unfilled close `IconButton`, which exits the entire flow and retains the draft. Once a name or avatar is chosen, its compact live preview and name occupy the title slot. A native linear indicator shows completed setup steps, switches to indeterminate only during an active submission or recovery request, and reaches completion only on a confirmed creation receipt. One route-group shell owns the creation model, header and footer while only nested step bodies slide horizontally. Progress animates on the UI thread and respects reduced motion. Android inputs use the shared filled native Compose `TextField` (see Forms) with floating labels and stable native composing state. Pinned actions use `KeyboardFormFrame`: a full-height body and an absolute `KeyboardStickyView` footer, matching the message composer. The active scroll reserves measured footer space; hidden steps stop keyboard processing. Native footer hosts ignore keyboard insets to avoid a second layout owner. Theme metrics subscribe only to font-scale changes, avoiding viewport-height invalidations across theme consumers. Compare actual keyboard transitions in non-debuggable Release builds before claiming an improvement. iOS keeps its native stack header and input adapter.
- **Avatar.** The Name page puts a large round avatar above the name field with Shuffle (a new generated pixel avatar) and Choose from Photos (256 px). Blank creation previews the generated avatar the name already gives; imports keep the avatar that ships with the Bot until the Human changes it. The choice stays in the draft; after the Bot is created the app applies it with the existing `botAppearanceSet` / `botAvatarSet` operations. If that fails the Bot stays created and a native alert says so.
- **Default Environment.** The only Environment, the one the Human entered from, or the last-used one (while reachable) is preselected; the Environment page still shows. Offline Environments are disabled. With none, an empty state offers Add Environment and returns with the new one selected.
- **Submitting.** Create shows the native indicator inside the capsule with “Creating…”, adds “Waiting for the Environment to respond” after about five seconds, and opens the new Bot, closing the step pages. A failure stays on the last page with the error above the bar and Retry; while the outcome is uncertain the same operation is checked again rather than resubmitted.

## Native Bot creation and import

Accepted scope, 2026-10-23. PR #2632 implements native blank creation and its recovery path; native qualification remains separate. The following contract also governs the remaining Git, Marketplace and Zip import slices tracked by #2634.

- **Distinct entry actions.** The Chats plus menu offers Create from scratch, Import Zip, Browse Marketplace and Import Git directly, in that order, with no visible menu heading. The plus anchors a UIKit UIMenu on iOS and a Material 3 DropdownMenu on Android; native menu items own highlight, dismissal and text scaling. Each opens its dedicated native step flow; Zip chooses its file on the page after the Environment (changed 2026-10-27, #2928). Leaving preserves the previous draft and destination. Unresolved submitted work takes precedence over a new entry and remains resumable. Existing cloud creation/join actions retain their scope.
- **Marketplace presentation.** A virtualized card feed shows each Bot's banner, overlapping illustrated avatar, name, repository/author, Bio, role tags and stars. Use the same seeded artwork as Web, including a deterministic banner fallback when artwork is missing or fails. Detail presents a larger social-profile header above import and README. On iOS, a transparent native navigation bar floats over the feed with only back and topic-filter glass circles and the automatic top scroll edge effect, as in Chat. There is no visible page title or painted header background. Sorting uses visible segmented tabs (readable option rows at larger iOS text sizes) above a horizontal strip of the six most-used topics, plus All and the active topic when outside that set. The filter sheet retains the full topic list, with an inset glass Close control on iOS and an opaque overlay body. The bottom-right search glass circle expands into a keyboard-tracking input row with explicit submit and close actions. Typing changes only the draft; submit refreshes the trimmed query (including repeated queries), and close clears search. Android retains its Material header, chips and sheet with opaque control fallbacks. Large system text wraps names, metadata and tags, with scrolling for all required actions.
- **Native flow.** Blank Bot creation, Bot Marketplace browsing and import, Git-link import, and Bot Zip import use native mobile pages. All four creation sources are in scope; the import sources match the desktop client.
- **Explicit destination from All.** The destination chooser lists all paired Remote Hosts, rather than only the currently active Host. The Human explicitly chooses the target. The most recently used Host may be preselected but never bypasses this choice; there is no separate default-creation-environment setting.
- **Inherit a selected Host.** Starting from Host A preselects A on the Environment step, which still appears so the Human sees and can change the destination (superseded 2026-10-27 by the step flow, #2924). This rule applies to blank creation and all three import sources.
- **Browse the Marketplace first.** Opening the Marketplace from All does not require choosing a destination. Choosing Import opens the destination choice and confirmation flow. Opening it from A carries A into confirmation. With phone network access, browsing remains available without a paired or reachable Host; import then offers pairing or connection while retaining the selected listing. Git-link and Zip drafts are also retained while the Human connects a destination. Restoring connectivity never automatically submits an unsubmitted draft.
- **Editable before submission.** The Human may change the destination before submission without losing the selected source or form contents. Submission fixes the destination and accepted input. Selecting another destination does not itself switch the app's browsing environment.
- **Import steps.** Marketplace, Git-link and Zip imports use the step flow above (superseded 2026-10-27, #2926/#2928). Marketplace and Zip names are prefilled from their source; Git has an explicit editable name. Source metadata is a default, never a replacement for a Human-edited name. Leaving the Git-link or Zip step checks the source on the chosen Environment; a failed check stays on that step with its error. The persona of an imported Bot comes from its source.
- **Open the result without taking over another page.** If the Human remains on the progress page, confirmed success switches to the destination Host and opens the new Bot's Human DM. If they have left, retain the completed result in the creation flow. Reopening it offers Open Bot; switch and navigate only when that action is chosen. Never show a global continuation footer below Home navigation. Cancellation before submission and failed creation leave the original browsing environment in place.
- **Leaving accepted work.** Once the Host has durably accepted the operation, it continues even if the Human leaves the page or the app. Returning to the operation reads its current state. Back means leave the progress view, not cancel server work. A hard-cancel action for accepted work is outside this delivery scope. Starting an HTTP request or displaying an upload indicator does not prove durable Host acceptance.
- **Zip upload.** While the file is still uploading, show progress and ask the Human to keep the app open. Preserve the selected file in app-managed storage as needed to recover across app restarts. If interrupted, reconcile the original operation and, when needed, upload the same content again under that operation; resumable byte-range upload and uninterrupted background transfer are not promised. Once the complete file is durably accepted for processing, the Host can finish without the phone remaining open.
- **Zip source and transfer.** The system document picker copies a selected archive into app documents before recording its opaque file ID, SHA-256 and size in the shared creation draft. Archives are limited to 100 MiB; hashing and uploads read at most 256 KiB at a time. The selected Host acknowledges the contiguous uploaded offset. Reopening the draft resumes from that Host's offset; expired staging restarts the same bytes. Preview returns metadata without creating a Bot, and an edited name survives another preview or target change. Submitted recovery checks the receipt before requiring the file. If the local copy is missing or changed, choosing the original archive restores only a matching hash and size while retaining the operation key, target and confirmed input. App-owned files are reclaimed after the shared record stops referencing them; unresolved and retained terminal operations keep their files.
- **Recover the same operation.** Reconnection and reopening the app recover the submitted operation on its original Host; retrying it cannot create a second Bot. An unreachable destination preserves the form and reports the connection problem rather than redirecting the mutation to another Host. [ADR-0247](../../docs/adr/0247-bot-creation-and-import-recover-on-their-chosen-host.md) owns durable recovery and authority.
- **Intentional additional copies.** Retry or recovery opens the original result. An explicit Import another copy action starts a separate operation and creates a fresh Bot, even for the same repository or Zip. Display names may repeat; the confirmation page lets the Human change them. Source or name equality is not an operation's identity.
- **Model readiness.** A new Bot follows the destination Host's default model settings. A missing or unusable model does not prevent creation or roll back a created Bot. Its DM clearly offers model configuration before conversation can proceed. Creating a Bot never automatically sends a model test message; successful creation and a successful model reply remain distinct evidence.
- **Existing ownership.** The selected Host owns the new PersonaBot and its Memory. Marketplace, Git and Zip imports create a fresh Bot through their existing Host-owned capabilities. The phone remains a client.

Product decisions for this scope are settled. The Host owns the operation states and reconciliation; the phone owns draft/selected-file retention, presentation and navigation. Read-only Marketplace access must work independently of a destination Host, through the mobile data layer rather than screen-owned network calls. Issues and PRs record implementation and runtime qualification for each source.

## Layers and states

Every fill comes from a layer, like the Web Client's DSH layers. `theme.layer.<name>` holds opaque colours:

| Layer    | Fill (DSH)           | Used for                                                  |

## System text and large-text acceptance

This contract applies to new and changed Expo/React Native screens, shared components and text/input adapters. It is a review requirement, not a claim that every existing screen or platform has already passed. The implementation details above remain version-specific; recheck them when React Native or Expo changes.

### Preserve platform ownership

- Use semantic text roles through our shared primitives. iOS follows native Dynamic Type; Android follows native text scaling, including nonlinear scaling on supported versions. Do not impose one JavaScript multiplier on every text style, scale the entire UI, or apply native and manual scaling twice.
- Do not disable scaling, shrink text to fit, change a title to a smaller semantic role at a breakpoint, or set a global `maxFontSizeMultiplier` to conceal a layout defect. A narrow exception must name the element, explain its purpose and accessible alternative, and carry native evidence in the PR. Existing decorative initials and hidden capture fields do not justify exceptions for visible content.
- Keep native navigation and Markdown as their own scaling owners. Reuse the documented shared adapter for framework bugs; avoid screen-specific font workarounds. Live setting changes must retain editable fields, drafts, focus and mention metadata. Record any selection limitation rather than claiming complete editing acceptance.

Platform references: [Apple Dynamic Type and adaptive layouts](https://developer.apple.com/videos/play/wwdc2024/10074/) and [Android nonlinear font scaling](https://developer.android.com/about/versions/14/features#non-linear-font-scaling). Follow documentation for the installed SDK/RN versions when choosing concrete APIs.

### Reflow the task, not only the text

- Let rows and controls grow using padding and minimum sizes. Wrap essential titles, action labels, validation and request details. Secondary previews may truncate only when complete content remains reachable; never hide the information needed to make an approval or form decision.
- Stack crowded metadata and actions; give the conversation, message or decision priority over decorative labels, timestamps and charts. Keep a stable semantic role when moving content. Move secondary detail behind an accessible entry rather than squeezing the primary content.
- Make sheets and forms scroll to their last option, error and action. Large headings must not consume a fixed part of the viewport. Preserve list virtualization; do not wrap a virtualized list in another scroll container to solve text overflow.
- Measure floating surfaces and reserve matching content insets. Test status bars, safe areas and keyboard-open states. Primary actions must stay reachable and text must not be hidden beneath chrome. Maintain at least the existing 44pt iOS / 48dp Android touch targets and meaningful accessible names.
- Bound inline editing so a long draft does not consume the task view. Provide scrolling and, where needed, expanded editing that shares the same draft, selection/mention handling and send path. Test returning, cancelling/dismissing and sending; do not create a second draft authority.

## Responsive interactions

Navigation, drawer/sheet opening, tab selection and editable search respond before waiting for data. Commit the destination's title, selected control and usable back/dismiss controls immediately. Defer expensive first content until the shell has had a frame to present, using `DeferredContent` for retained page content; never add an arbitrary animation-duration timeout or await a network call before opening.

- Prefer the last successful content for the same Host and query while refreshing. An uncached result shows a bounded, noninteractive skeleton in its final layout; distinguish loading, empty, failure and content. A failed refresh keeps the content with a retry notice. Query identity includes every filter; changing Host must never reuse another Host's content. Bound inactive caches and release subscriptions when their page loses focus. Shared Host transport continues receiving.
- Prefetch a likely destination during idle time or intent when it helps the measured first visit. Deduplicate with the same cache the destination reads, cancel obsolete ownership and keep prefetch off the critical press path. Prefetch is an optimization, not a prerequisite for navigation.
- Separate focus/status-bar/chrome updates from expensive content. Preserve list, pager and editable-field identity across focus changes so scroll positions, choices and drafts survive. Memoization must address a measured invalidation and keep meaningful inputs stable; do not suppress updates with incomplete comparators.
- Android streaming bubble growth uses one native paint boundary for the background and visible children (120ms). Text/list layout retains its final bounds; paint frames never request layout or duplicate text. Static/reduced-motion bubbles use ordinary Views. iOS retains its existing surface until separately implemented and verified.

- Virtualize long chat, roster and Activity lists. Streaming publishes update the active draft/tail; historical messages keep stable keys and avoid re-rendering for a pure tail append. Reading history owns its cursor until the user deliberately returns to the bottom. Exercise both history scrolling and scrolling during streaming.
- Measure tap-to-first-feedback and data-ready time separately, for cold, prefetched, warm/cached, slow and failed requests. Record the build, input size, query, device and instrumentation. Target 120 FPS means an 8.33 ms frame budget: report native presented-frame intervals/hitches and JS work separately, with the existing ABBA/three-run method. Development profiles identify work; production JavaScript on a Debug binary and a native Release build are different results. A 120 Hz setting, a skeleton screenshot or a smooth recording cannot qualify 120 FPS.

The shared Expo/React rules are platform-independent; native iOS and Android acceptance remain separate. Reference: [Expo prefetch behavior](https://docs.expo.dev/router/basics/navigation/#prefetching) and [React deferred rendering](https://react.dev/reference/react/useDeferredValue). Use APIs from the installed SDK source when current documentation differs.

Returning to the foreground requires a new gesture; no queued wheel input is replayed.

The Android Local Computer page keeps its surrounding canvas and safe-area background pure
black in both app appearances, with a scoped dark theme for readable controls. Its leading
native tonal Back button exits Computer and sits `space.x3` away from a separate capsule
containing the current paired Host environment name (including its local display alias),
following the chat header's island layout. The header has no opaque band; the Back fill
and capsule reuse chat header material. A native computer symbol identifies the environment.

while waiting for video, and muted while disconnected. Native person/Bot/pause/unknown icons
distinguish control authority; no secondary status text is displayed. Disconnection clears
the previously observed controller indicator. Full state remains available to accessibility.
The capsule identifies the Computer; it is not another action. Status-bar icons stay light
only while this screen is focused. Take control / Hand back is the filled primary action;
keyboard visibility is a native Material icon toggle and Reset is a native icon button.

HorizontalFloatingToolbar with minimum 48 dp controls and horizontal scrolling for

### Local Computer click feedback

Preview taps, long-press right-click and the two mouse buttons share the same click path.
After the Host acknowledges a click in the current viewer/grant, a 300 ms local ring expands
and fades at that click's remote coordinate: blue for Left, orange for Right, with a dark rim
for visibility over the desktop. The ring follows preview transforms but not later cursor
motion. Wheel drags, refused or uncertain clicks produce no acknowledgement ring. A new
click restarts the short feedback; losing control hides it and a new viewer never replays
an old click. Reanimated runs transform/opacity on the UI thread. Reduce Motion replaces
expansion/fading with a static ring for the same brief interval. This feedback confirms
input delivery, not whether the target application completed a business action.

### Local Computer native keyboard

Android Local Computer uses a nonvisual native InputConnection target for the system keyboard. Compose TextField and React Native TextInput are local editors, not committed-IME event sources; a custom native target is needed to forward committed text and native deletion without displaying a second field or Send row. Composition remains inside the phone IME until committed. Native focus belongs to the explicit keyboard session, not React editor refs or video updates. Back/hide, background and control loss discard unfinished composition. Input stays inside the current Computer grant and ordered no-replay queue; an uncertain input closes keyboard capture. The preview and Hand back remain reachable while typing. This adds a native module and requires a rebuilt Android app.

iOS uses the same RemoteKeyboard contract and queue, backed by a nonvisual UIKit text input. Marked-text composition stays in the system input method until committed; committed text, Return and Backspace go through the existing granted input path. Closing, backgrounding or replacing a keyboard session discards unfinished composition, and a dismissed session never refocuses itself. The Apple adapter requires a rebuilt iOS app.

### Android group invitation drawer

### iOS workspace panel (#3017)

The Human clarified this presentation on 2026-10-28: both directions must follow the finger, and merely looking at Workspaces must preserve the selected environment and the mounted Chats list. This replaces the earlier Mail-like stack root because popping Chats destroyed that route and returning pushed a fresh one. It is an application-defined adjacent-page presentation, not an iPhone sidebar API or a second source of workspace authority.

- The first page is Workspaces, without the bottom tab bar. The next page contains the existing tab navigator **and its bottom tab bar**, so the list and bar move as one native page. The React page trees remain mounted. Chats can continue left into the last visited chat and then its profile; returning reverses the same native pages. Each chat/profile uses the existing UIKit navigation bar with an independent Back before the identity Chip and a masked native top material that extends below the bar. No skeleton preview, custom per-frame translation, pop/push, route reset or Host selection runs when a person only swipes between them.

The Chats title opens Workspaces with a native page command. Reduced Motion uses the existing live system preference and the native nonanimated page command for button navigation. The native pager dismisses the keyboard on drag without clearing search text.

### Workspace history transitions (#2800)

Explicit workspace selection resets the root history only after source selection succeeds. `workspace-navigation.ts` retains the existing two-tab route and its page keys, selects the Chats root, and removes scoped details and sheets. A Cloud workspace occupies one list route above those retained tabs; selecting the same scoped workspace reuses that route key. Failed selection leaves the previous state untouched.

`native-workspace-navigation.ts` binds that adapter to the mounted root navigator and observes existing Host/Cloud authorities. Removing/replacing a pairing or changing an instance/account removes affected routes; selecting a different current Host or refreshing the same Cloud account does not. Notification and ordinary Channel navigation preserve their S1/S2 histories. Drawer Host, All and Cloud choices share one intent guard, so obsolete asynchronous source selection cannot navigate after a newer choice or root unmount. No cache or draft store is cleared by navigation. See #2186 for the separate broader workspace platform/role acceptance matrix.

Cloud organization access may rotate and persist issued credentials while a selection is pending. Cancellation checks run before access and before route reset; they do not discard issued refresh tokens. The active workspace is the explicit route/filter, so a late same-account credential refresh cannot select Cloud after All/Computer. CloudClient refuses concurrent mutations with SESSION_BUSY; a later Cloud choice resolves its requested Organization again.
